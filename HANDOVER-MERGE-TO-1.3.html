四、冲突解法（核心，按这个做就行）

4.1 后端：3 个冲突，全部取 1.3.0 的版本

冲突文件：

encore-api/go.mod
encore-api/go.sum
encore-api/l1-access/authn/auth.go

解法：三个都取 1.3.0 那一侧（ours）。

git checkout --ours encore-api/go.mod encore-api/go.sum encore-api/l1-access/authn/auth.go
git add encore-api/go.mod encore-api/go.sum encore-api/l1-access/authn/auth.go
cd encore-api && go mod tidy && cd ..

为什么取 1.3.0 而不是合并：

  1. authn/auth.go 两边的函数签名根本不同，不能文本合并。 - 1.3.0：func AuthHandler(ctx context.Context, params *AuthParams) —— Encore 原生 auth handler - 自动化分支：func AuthHandler(ctx context.Context, token string) —— 旧的自定义中间件写法 - 而且 1.3.0 把会话校验拆到了单独的 community_session.go（106 行），自动化分支是写在 auth.go 里的。 两份是同一件事的两种写法，选 1.3.0 的（更新、符合 Encore 规范）。

  2. go.mod / go.sum：1.3.0 是超集。 1.3.0 有 casbin、go-oidc、paho.mqtt、golang-jwt、pgx v5.7.2、go-redis v9 等； 自动化分支只多了一个 pgx v5.2.0（旧版本）。取 1.3.0 后再 go mod tidy 补齐即可。

已实际验证：按上述方式解决后，encore-api 目录 go build ./... 编译通过， 说明自动化服务的代码与 1.3.0 的 authn 实现兼容，不需要改 automation 包。 仓库根目录（社区后端）go build ./... 同样编译通过。

4.2 前端：2 个冲突，一个取我方、一个手工

① src/views/automation/linkage-edit/modules/edit-action.vue —— 取自动化分支

git checkout --theirs src/views/automation/linkage-edit/modules/edit-action.vue
git add src/views/automation/linkage-edit/modules/edit-action.vue

原因：1.3.0 这一侧是空的，自动化分支在这里加了 placeholderMap（动作值输入框的示例值）。 取我方即可，没有需要保留的对方内容。

② src/views/alarm/warning-message/components/pop-up.vue —— 不能机械解决，按下面三步

这个文件是唯一需要动脑子的地方。背景：

  • 1.3.0 在这一版里新增了"租户默认策略"选择器（+143 / −80 行），是别人做的功能，不能丢。
  • 自动化分支在这一版里只改了 6 行：把告警接口从旧 @/service/api/alarm 换成新引擎的 @/service/api/alarm-native。

第一步：以 1.3.0 为基线

git checkout --ours src/views/alarm/warning-message/components/pop-up.vue

第二步：改 import（第 13 行附近）

- import { addWarningMessage, editInfo } from '@/service/api/alarm'
+ import { addWarningMessage, editInfo } from '@/service/api/alarm-native'

第三步：改返回值判断（约第 313 行，addWarningMessage 调用处）

  const res = await addWarningMessage(data)
- if (res) {
+ if (res.data) {

这一步千万不能漏。 两个接口的返回形状不同：

  • 旧 alarm.ts 的 addWarningMessage 返回裸对象，if (res) 判断的是"有没有返回"。
  • 新 alarm-native.ts 返回 { data, error }（FlatResult）。res 永远是非空对象， if (res) 永远为真 —— 不改的话，添加失败也会弹"添加成功"。

editInfo 那边是 const { data } = await editInfo(datas)，FlatResult 本身有 data 字段， 所以不用改，但合并后要确认它确实是解构 data 而不是整个对象。

git add src/views/alarm/warning-message/components/pop-up.vue

已实际验证：按上述方式解决后，这两个文件 eslint 检查 0 error （只剩一条原有的 'e' is defined but never used warning，与本次无关）。

5.1 补一条菜单记录（已有环境必做，新装环境自动带上）

前端是动态路由，路由完全由后端 sys_ui_elements 表下发。 规则编辑页 /automation/rule-edit 不在表里，客户从设备详情点"生效规则"里某条规则，会直接看到 404。

5.2 网关加一条反向代理（生产必做）

前端默认同源访问自动化服务，前缀 /automation-core，由反向代理剥掉前缀转发。

location /automation-core/ {
    proxy_pass http://<自动化服务地址>:<端口>/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header Authorization $http_authorization;
}

不加这条，所有自动化页面 404。

如果不想用同源反代，也可以在构建时给绝对地址：

VITE_AUTOMATION_API_BASE_URL=https://automation.example.com npm run build

十一、本次改动里最值得看的两处（review 重点）

如果只想看关键 diff：

① 87e6aef7 上报链路按开关切换新引擎 旧引擎和新引擎此前是两条互不相干的路径。要切就必须二选一，否则一条遥测会触发两次真实下发， 设备收到两遍命令。用一个值决定（GOTP_AUTOMATION_MODE），默认 legacy。 转发走有界队列 + 4 worker，队列满则丢弃并计数——慢引擎的代价是丢自动化事件，不是拖慢遥测。

② 5697a462 命令受理守卫移到响应中间件之外 守卫原来注册在 handler.Middleware() 里面，它自己写响应头后，响应中间件跳过加成功包， 调用方拿到空体 200；自动化服务把空体读成 code 0，于是每条命令都记 command_rejected ——而设备其实已经动作了。症状极隐蔽：MQTT 上命令确实到了，运行记录却是失败。 已补回归测试锁住中间件顺序。
