## 做了什么
- **插件升级走现有的“代次”机制，没有第二套**：`Engine.Upgrade` 只允许运行中（enabled）的插件，目录里的版本和已装版本不同才允许；它把行放回 `installing` 并开始一次新操作，由原有的 `install` 流程完成：发新代次身份 → Agent 接受新代次（旧代次被吊销并退役）→ 按**当前**签名目录条目准备、授权、激活新容器 → 健康检查。**只有新代次健康后才把已装版本改成新版本**（`reconcile.go` 里成功路径记录 `CatalogVersion`）；站点配置和密钥保持不变。
- **镜像预检**：Agent 的目录列表现在带 `image_present`；后端在镜像缺失时拒绝升级（409 `IMAGE_UNAVAILABLE`），**不会动正在运行的插件**。原因：现有流程在准备新代次**之前**就吊销旧代次，镜像拉不到会让插件停机。
- **接口**：`GET /api/v1/plugin/catalog` 的每项多了 `update_available`、`image_available`；`POST /api/v1/plugin/installs/:id/upgrade`（仅平台超级管理员，错误 `UP_TO_DATE`/`BAD_STATE`/`IMAGE_UNAVAILABLE`/`AGENT_OFFLINE`/404）。
- **界面**：“检查更新”里，平台、tp-agent 之后列出需要升级的插件（当前版本 → 新版本 [升级]），确认框写明会短暂停止插件，行内显示进度/成功/失败+重试，不进维护遮罩。
- **统一列表怎么拼**：平台和 tp-agent 来自 Encore 的 `/api/system/updates`，插件来自 Gin 的 `/api/v1/plugin/catalog`，由前端拼在一起。**没有**让 Encore 去调 Gin（避免新增“旧接口桥”）。

## 怎么验证的
**单元测试**（不等于整栈验收）：`plugininstall` 的引擎测试（假 Agent + SQLite）：升级后代次 +1、旧代次被吊销和退役、新版本被记录、站点密钥仍在；相同版本拒绝；非运行状态拒绝（停止的插件仍显示有新版本）；别的租户拿不到行；**升级失败（准备阶段被拒）时保持旧版本记录、没有存活的身份、重试能完成**；镜像缺失时拒绝且旧代次不被触碰，镜像补上后可升级。Gin 路由测试（非管理员 403、未知 404、非运行状态 409）。Agent 测试：目录列表按本机镜像存在与否报告。Go 全套 `-race` 通过；前端新增 9 条单元测试（见前端说明）。

**真实整栈演练**（隔离栈 `r7`，后端用本分支构建，Agent 为本分支二进制，目录由我自己的密钥签名，真实浏览器）：
- **替身插件**：本机没有真正的 Home Assistant 插件镜像，所以用同样目录条目格式（id `homeassistant`）的小镜像（busybox 静态 HTTP 服务，版本 1.0.0/1.1.0/1.2.0）代替。**机制与真实 HA 插件相同，但没有对真实 HA 连接器镜像升级过。**
- **API 层**：安装 1.0.0（代次 1，`health ok`）→ 发布 v2 目录 → `update_available:true` → 升级 → 代次 2、版本 1.1.0、新容器；**旧代次续租被 Agent 拒绝（409 “execution generation is lower than persisted maximum”）**，旧容器已不存在。
- **界面**：更新对话框同时列出“ThingsPanel 平台 已是最新”“tp-agent 请用安装器升级”“插件：Home Assistant 1.1.0 → 1.2.0 [升级]”；确认后行内“升级中…”，之后“升级成功，当前版本 1.2.0”，后端侧代次 3、旧代次被拒、本实例只剩一个容器（截图 1–3）。
- **镜像缺失**：发布一个指向不存在镜像的 1.3.0 目录 → `update_available:true, image_available:false`；点升级得到 409 `IMAGE_UNAVAILABLE`，插件保持 enabled、代次 8、版本 1.2.0 不变。

## 演练里发现的问题
1. **准备阶段失败不会立刻判失败，而是当成“Agent 离线”重试**：第一次我没做镜像预检，用不存在的镜像升级，状态一直是 `installing`（`error_code: agent_offline`，步骤 `agent_prepare`），每次重试代次 +1（最多 40 轮、退避到 4 分钟），**这段时间插件是停着的**（旧代次已吊销）。这是原有的 `install` 行为（Agent 的准备错误被归为可重试），不是 R7 引入的；R7 用镜像预检挡住最常见的原因，没有改这条重试规则。已写入 TODO。
2. 更新对话框里插件升级成功后那一行仍显示“1.1.0 → 1.2.0”（按钮置灰），没有重新拉取目录；功能正确，只是文字没刷新（前端，小问题）。

## 没做 / 没验证（如实）
- **没有自动回退到旧版本**：Agent 只认识当前目录，旧版本的目录条目不在了，所以失败的升级停在 `failed`（版本记录仍是旧版本），只能“重试”或手动处理。计划里 §4.3 写的“新代次先准备再吊销旧代次”也**没有做**：Agent 的代次模型里接受新代次就会让旧代次过期，两个代次不能并存。
- **新目录怎么到达 Agent**：现在是把签名目录文件放到 Agent 挂载的目录（Agent 每次请求都重读）。通过安装器/发布流程分发新目录和镜像的链路不是这张卡的范围。
- **真实 HA 插件镜像**没有升级过（见上，用替身）。
- 升级会停止插件，设备连接在此期间中断；没有测量中断时长，也没有缓冲。
- 平台那一行和插件那一行仍是两个接口拼出来的；等插件安装迁到 Encore 后再合并成一个（TODO）。
- 老 Gin：这次在已有的 `plugininstall` 引擎（不依赖 gin）上加了方法，在 Gin 路由里加了一个端点；它和插件安装的其余部分一起，将来要随 Gin 被替换而迁到 Encore。
