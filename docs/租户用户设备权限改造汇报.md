# ThingsPanel 租户与用户设备权限改造汇报

## 一、交付结论

本次已完成 ThingsPanel 社区版“租户内不同用户管理不同设备”的最小可用闭环：

- 租户管理员可以在用户管理中为普通租户用户逐台设置“无授权 / 只读 / 管理”。
- 普通用户的设备列表、设备选择器、设备详情、指标/遥测、在线状态、设备组关系均只返回已授权设备。
- 设备修改、删除、凭证、连接信息、配置切换、子设备绑定、人工命令下发均要求该用户对目标设备具备“管理”权限。
- 新建用户默认没有设备权限；数据库迁移会为已有 `TENANT_USER` 回填原有租户内的设备管理权限，避免上线后突然丢失存量用户能力。
- 租户边界仍由服务端 Claims + `tenant_id` 校验决定，前端隐藏按钮不承担安全职责。

## 二、修改思路

采用“租户硬隔离 + 用户设备范围 + 读写分级”的渐进实现，复用现有用户、设备、设备组和 Casbin 功能权限：

1. 新增 `user_device_permissions` 表，以 `(user_id, device_id)` 为唯一授权关系，记录 `tenant_id` 和 `access_level`。
2. 新增用户设备权限查询/全量替换 API：
   - `GET /api/v1/user/{id}/device-permissions`
   - `PUT /api/v1/user/{id}/device-permissions`
3. 设备列表在分页、排序、统计前先按授权设备 ID 过滤，避免“列表看不到但总数泄露”或空页问题。
4. 详情、更新、删除、连接凭证、指标、遥测、命令、子设备等入口统一复用设备访问检查。
5. 前端用户管理增加“设备权限”弹窗；设备管理页对普通用户隐藏“新增设备”入口，但后端仍保留硬校验。

## 三、场景验证

### 场景：张三只能管理 A 组，李四只能查看 B 组

改造前：

- 用户角色主要控制菜单和功能，设备业务接口通常只按租户过滤。
- 同一个租户内的普通用户可能看到租户下全部设备，不能可靠区分设备管理范围。

改造后：

- 管理员打开“用户管理 → 张三 → 设备权限”，给 A 设备选“管理”，不给 B 设备授权。
- 张三登录后，`GET /device` 的列表和 `total` 只包含 A 设备；访问 B 设备详情、修改或下发命令统一返回无权限。
- 给李四的 B 设备选“只读”后，李四可以查看 B 的详情、指标和在线状态，但修改、删除、凭证和人工命令下发会被拒绝。
- 撤销授权后，后续请求立即以数据库当前授权为准；已在途的设备物理动作不由本次改造承诺回滚。

## 四、验证结果

已执行：

- `go test ./internal/service ./internal/dal ./internal/api ./router/apps`：通过。
- `go test $(go list ./... | rg -v '^project/test$')`：通过。
- `go vet ./...`：通过。
- `pnpm build:test`（含项目自带 typecheck）：通过，构建成功。
- 单独执行 `pnpm exec vue-tsc --noEmit --skipLibCheck` 会暴露仓库基线类型问题；复核输出后仅命中设备管理页原有回调签名错误，未命中本次新增权限弹窗、用户管理接口或权限字段改造。
- `git diff --check`：通过。

未能通过的原始命令：

- `go test ./...` 会进入仓库既有 `test/pg_test.go`；本机没有该测试所需环境时先报“未知环境”，随后对空数据库连接解引用导致 panic。该失败发生在既有数据库测试初始化，不是本次权限代码编译或测试失败；已用排除 `project/test` 的全量测试完成验证。

手工验收建议：

1. 执行 `migrations/009_create_user_device_permissions.sql`。
2. 以租户管理员登录，创建两个普通用户和至少两台已激活设备。
3. 分别给两个用户配置不同设备的只读/管理权限。
4. 分别登录两个用户，验证设备列表、设备详情、指标、设备选择器只显示授权设备。
5. 对只读用户尝试修改、删除、换凭证、切换设备配置、下发命令，确认接口拒绝且没有产生设备副作用。
6. 重新保存权限为空，确认该用户设备列表为空；再恢复一条权限，确认访问恢复。

## 五、结构、可靠性与可能退化

收益：

- 授权关系单独建表，不污染现有 `users`、`devices` 主表，也不把设备 ID 塞进 JWT。
- 查询过滤和单资源检查共用同一授权事实源，列表、详情、写操作边界更一致。
- 全量替换权限具备事务性；跨租户设备 ID、重复设备授权、非法权限级别会被拒绝。
- 保留现有 Casbin 的功能权限，同时补齐其无法表达的设备实例范围。

风险/限制：

- 本次是一期最小闭环，授权粒度为“用户 × 单设备”，尚未实现设计方案中的用户组绑定、项目范围、字段/命令 allowlist、授权版本缓存、审计和完整迁移报告。
- 非管理员用户的授权设备 ID 当前会先读入服务端再参与查询，适合当前规模；设备量很大时建议升级为 SQL `EXISTS` 子查询或授权投影表。
- 存量用户回填为 `manage` 是兼容性选择，不代表最小权限；上线后应按业务逐步收紧。
- 数据库迁移尚未在真实 PostgreSQL 实例执行，本地没有可用 PostgreSQL 测试环境。
- 后台自动化调用保留独立的可信内部命令入口；后续应按设计继续引入 execution grant 和 worker 复核，不能把内部调用入口暴露给 HTTP。

## 六、业务价值

- 对客户：可把设备按人员职责分配，减少误操作和跨岗位数据暴露，适合园区、学校、工厂、连锁门店等多角色协作场景。
- 对租户管理员：新增用户不再天然看到全租户设备，可在一个页面完成授权调整，人员变更不需要逐台改设备。
- 对 ThingsPanel 产品：从“菜单级角色”推进到“功能角色 + 设备范围”，为 SaaS 多租户、渠道交付和项目化部署提供可销售的权限能力。
- 对市场与商业：可以进一步包装现场操作员、只读观察者、设备管理员等岗位方案，支撑最小权限、安全合规和更清晰的租户分层定价。

## 七、下一步方案对比与建议

| 方案 | 适用场景 | 优点 | 成本/风险 |
|---|---|---|---|
| A. 继续完善单设备授权 | 设备量中小、快速交付 | 低改造成本，规则清晰 | 授权记录随设备和人数增长，批量管理较弱 |
| B. 用户组/设备组范围授权（推荐） | 学校班级、工厂产线、园区区域 | 一次授权多人，符合设计方案，维护成本低 | 需要组树、成员变更、范围继承和完整测试 |
| C. 完整 RBAC + 项目 + 字段/命令限制 | 大型 SaaS、强合规客户 | 权限表达能力最完整，支持岗位和高风险控制项 | 需改造看板、告警、自动化、导出、WebSocket 和审计，周期最长 |

建议下一步选择 B：保留本次单设备授权作为特例，新增“用户组 × 设备组 × 角色”的绑定，并让单设备授权作为特殊范围落地。这样既能覆盖“张三管 A 组、李四管 B 组”，又避免管理员逐台勾选；完成后再按 C 的优先级收口看板、自动化、导出和字段/命令权限。
