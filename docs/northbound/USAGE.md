# 北向服务（数据转发）使用说明

这份文档讲**怎么用**：从哪儿进、每一步点什么、数字怎么看、出错怎么办。
部署与升级见 `DEPLOYMENT.md`，值班与故障定位见 `MAINTENANCE.md`。

---

## 1. 入口与权限

左侧菜单 **数据服务 → 数据转发**，页面路径 `/data-service/northbound`。

页面有四个标签页：

| 标签页 | 干什么 |
|---|---|
| 总览 | 一眼看全：连接器健康、等待投递数、因容量未登记数、本机源端状态 |
| 目标连接 | 数据往哪儿送（HTTP 接口 / MQTT Broker），凭证与连通性 |
| 转发任务 | 哪类数据、经过什么处理、送到哪个连接 |
| 投递记录 | 每一条投递的实际结果，以及人工重放 |

权限沿用社区既有角色，**不新建身份**：

| 角色 | 看 | 改配置 | 重放 |
|---|---|---|---|
| `tenant_admin` | ✓ | ✓ | ✓ |
| `tenant_operator` | ✓ | ✗ | ✗ |
| `tenant_viewer` | ✓ | ✗ | ✗ |
| `platform_admin` | ✓ | ✓ | ✓ |

`tenant_operator` 和 `tenant_viewer` 看得到全部页面，但新建/修改/启停/重放的按钮
点下去会返回 `permission_denied`（HTTP 403）。

## 2. 五分钟跑通一条

### 第 1 步：建目标连接

「目标连接」→ 新建 → 选连接器（HTTP 或 MQTT）→ 填表单。

表单是**按插件声明的 JSON Schema 生成的**，不是硬编码的固定字段。插件升级加了
字段，页面自动多出输入框，前端不用跟着改。

HTTP 连接器最小配置：

| 字段 | 说明 | 例子 |
|---|---|---|
| 目标地址 | 必须是完整 `http/https` 地址 | `https://api.example.com/ingest` |
| 请求方法 | 只支持 POST / PUT | `POST` |
| 幂等头名称 | 平台会把幂等键放在这个请求头里 | `Idempotency-Key` |
| 超时 | 毫秒 | `5000` |

MQTT 连接器最小配置：

| 字段 | 说明 | 例子 |
|---|---|---|
| Broker 地址 | `tcp://` 或 `ssl://` | `tcp://broker.example.com:1883` |
| 主题模板 | 可用 `{deviceId}` 占位 | `devices/{deviceId}/telemetry` |
| QoS | 0 或 1 | `1` |

凭证字段（密码、Token、客户端密钥）**保存后不再回显**。编辑时留空表示「不修改
已保存的凭证」，不是「清空」。

保存后点 **测试连接**。它会真的去校验配置并打开目标，返回三项检查结果。**这一步
不通过就别往下走**，后面所有投递都会失败在同一个原因上。

### 第 2 步：建转发任务

「转发任务」→ 新建。新建出来是 **草稿（draft）**，草稿不产生任何投递。

| 字段 | 说明 |
|---|---|
| 目标连接 | 第 1 步建的那个 |
| 数据类型 | 遥测 / 属性 / 事件，可多选 |
| 设备范围 | 留空 = 全部设备；填了就只转发这些设备 |
| 只保留字段 | 白名单。留空 = 全保留 |
| 排除字段 | 黑名单 |
| 脱敏字段 | 这些字段的值会被替换掉，不出现在目标侧 |
| 字段改名 | JSON 对象，如 `{"temperature": "temp_c"}` |
| 附加固定字段 | JSON 对象，如 `{"site": "hangzhou"}` |
| 包装字段名 | 填了就整体包一层，如填 `data` → `{"data": {...}}` |

### 第 3 步：预览

粘贴一条源端事件信封（JSON），点 **预览**。页面会显示：

- **命中 / 未命中**，未命中时给出原因（哪个条件没过）
- **最终会发出去的字节**——不是原始事件，是套完过滤、改名、脱敏、包装之后的
- **幂等键**

预览**不发任何数据**，可以随便点。

### 第 4 步：启用

点 **启用**，任务从 `draft` 变 `active`，开始对**新**数据生成投递。

想先确认链路通不通，可以用 **测试发送**：它会把样例事件真的发一次，产出一条真实
投递记录。测试发送和预览的区别见第 4 节。

## 3. 每个页面看什么

### 3.1 总览

四张数字卡 + 两张表：

| 数字 | 含义 | 变大说明什么 |
|---|---|---|
| 等待投递 | 已登记、排队等着交接 | 交接链路堵了，看本机源端表的「最近错误」 |
| 已送达 | 目标确认收到 | 正常 |
| 结果未知 | 发了但没拿到确定答复 | 要人工判断，见第 5 节 |
| 因容量未登记 | 当时被直接拒绝，**没进任何队列** | 积压超限或事件太大，这些数据不会补发 |

下面还有两张表：**连接器**（每个插件的真实健康状态，不是配置里的声明）和
**本机源端（社区运行侧）**（接入方式、已订阅租户数、等待/已交接/失败计数、
最近成功与最近错误的时间）。

如果页面顶部出现一条警告「当前接入方式（xxx）不具备持久接收边界」，说明社区后端
的 `mqtt.input_profile` 不是 `ingress_v1`。这种情况下**不会产生任何投递记录**，
不是故障，是这套接入方式本来就没有持久接收承诺。

### 3.2 目标连接

列表显示名称、连接器、状态、是否有凭证、版本号、更新时间。

| 状态 | 含义 | 怎么办 |
|---|---|---|
| 可用（active） | 正常 | — |
| 需修复（needs_repair） | 上次投递被目标拒绝（典型是 401/403），或配置校验失败 | 改凭证/配置 → 测试连接 → 恢复 |
| 已停用（disabled） | 人工停用 | 需要时启用 |

连接被标记为「需修复」时，**该连接上的任务会停止投递**，积压保留。修好后积压会
继续发，不用手工重放。

### 3.3 转发任务

列表显示状态、目标、积压、生效版本。

| 状态 | 新数据会不会转发 | 已有积压会不会继续发 |
|---|---|---|
| 草稿（draft） | 不会 | 没有积压 |
| 转发中（active） | 会 | 会 |
| 已暂停（paused） | **不会** | **会** |
| 已停用（disabled） | 不会 | **不会**（积压保留） |

**「暂停」和「停用」的区别就在积压上。** 暂停是「先别接新活了，手上的干完」；
停用是「全部停下」。想彻底止血用停用，想平滑切换用暂停。

改配置会让生效版本 +1。**已经排队的投递仍按它当初那一版执行**，不会因为你现在
改了字段映射就变。

### 3.4 投递记录

每条记录一行：事件 ID、设备、任务、状态、尝试次数、失败原因、确认级别。

状态说明：

| 状态 | 含义 | 会自动重试吗 |
|---|---|---|
| 等待（pending） | 排队中 | — |
| 重试等待（retry_wait） | 上次失败，等退避时间到了再试 | 会 |
| 未知（unknown） | 请求发出去了，没拿到确定答复 | **不会**，必须人工判断 |
| 死信（dead） | 目标明确拒绝（4xx 之类）或重试次数用尽 | 不会，只能人工重放 |
| 已送达（delivered） | 目标确认收到 | 不会重放 |

**确认级别**这一列很重要：

- `destination_acked`：目标确实确认收到了（HTTP 2xx、MQTT QoS1 的 PUBACK）
- `none`：发出去了但没有确认（MQTT QoS0）。**这不等于送达**，页面不会把它算成
  已送达。

## 4. 三个容易搞错的概念

### 4.1 「等待投递」和「因容量未登记」

这两个数字**必须分开看，也确实是分开的**：

- **等待投递**：数据已经写进 Outbox 并提交了事务，排在队里等交接。**会继续发。**
- **因容量未登记**：当时积压超限或单条太大，直接拒绝，**没有进任何队列**。**不会补发。**

把这两个数加在一起叫「待发送」是错的：一个会到，一个永远不会到。总览页把它们
放在两张卡里，就是为了不让人混。

### 4.2 「预览」和「测试发送」

| | 预览 | 测试发送 |
|---|---|---|
| 会不会真的发出去 | 不会 | **会** |
| 会不会产生投递记录 | 不会 | 会 |
| 会不会被目标收到 | 不会 | **会** |
| 能不能反复点 | 能 | 会污染真实数据，别乱点 |
| 需要什么状态 | 草稿也能用（但需先保存） | 任务要已启用 |

上线前先用预览确认「发出去的字节对不对」，再用测试发送确认「链路通不通」。

### 4.3 「任务暂停」和「连接停用」

- 任务暂停：只影响这一个任务，其它任务照常。
- 连接停用：这个连接上的**所有任务**都停。

排查某个目标出问题时用连接级；只调某一个任务的规则时用任务级。

## 5. 结果未知（unknown）怎么处理

`unknown` 的意思是：请求已经发到目标了，但平台没拿到确定的答复（超时、连接被
中途掐断、目标返回了看不懂的东西）。**这时候目标可能已经写入了，也可能没有。**

平台**故意不自动重试** `unknown`。理由很直接：自动重试可能在目标侧造成第二次
业务写入，而平台无法替你判断这件事能不能接受。

处理步骤：

1. 到目标系统查一下这条数据在不在（用页面上的事件 ID 或幂等键去查）。
2. **不在** → 在投递记录里点 **重放**，填原因，提交。会重新排队。
3. **在** → 不需要动作。这条记录留着当证据。
4. **查不了 / 不确定** → 重放时会出现一个勾选框「确认重复写入风险」，勾上才能提交。
   勾选表示你接受目标侧可能被写两次。

重放有几个硬约束：

- 必须填**重放原因**，会记进审计信息。
- **幂等键不变**。目标侧如果按幂等键去重，重放不会产生第二次业务效果；如果目标
  不认幂等键，那就是真的写了第二次——这正是要你确认风险的原因。
- `delivered` 的记录不允许重放。

## 6. 一个事件匹配多个任务时会发生什么

会**分别**生成投递，每条独立记账、独立重试、独立确认。

**一个任务成功了，不会把另一个任务的待办清掉。** 这是刻意的：如果任务 A 送到
HTTP 接口成功、任务 B 送到 MQTT 失败，B 必须继续重试，不能因为「这个事件已经
处理过了」就跳过 B。

在投递记录里按事件 ID 过滤，能看到这个事件派生出的全部投递行，各自的状态互不
影响。

## 7. API 速查

浏览器路径前缀是 `/api/v1/northbound`，社区后端纯代理到 Encore 的 `/v1`。
以下用 curl 直连 Encore 演示（`$T` 是社区令牌，`$E` 是 Encore 地址）。

```bash
# 总览
curl -s -H "Authorization: Bearer $T" $E/v1/overview

# 连接器目录（含真实健康）
curl -s -H "Authorization: Bearer $T" $E/v1/connectors

# 建连接
curl -s -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"name":"订单系统","connectorId":"io.thingspanel.sink.http",
       "config":{"url":"https://api.example.com/ingest","method":"POST",
                 "idempotencyHeader":"Idempotency-Key","timeoutMs":5000}}' \
  $E/v1/connections

# 测试连接（真去打开目标）
curl -s -X POST -H "Authorization: Bearer $T" $E/v1/connections/<id>/test

# 建任务（草稿）
curl -s -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"name":"温度转发","connectionId":"<id>",
       "filter":{"eventTypes":["telemetry"]},
       "transform":{"include":["temperature"],"rename":{"temperature":"temp_c"}},
       "serialization":{"format":"json"}}' \
  $E/v1/pipelines

# 预览（不发送）
curl -s -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"sample":{...事件信封...}}' $E/v1/pipelines/<id>/preview

# 启用
curl -s -X POST -H "Authorization: Bearer $T" $E/v1/pipelines/<id>/activate

# 投递记录（按状态过滤）
curl -s -H "Authorization: Bearer $T" "$E/v1/deliveries?state=unknown&limit=50"

# 重放（必须带原因；unknown 还要 acknowledgeRisk 或强幂等连接器）
curl -s -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
  -d '{"reason":"目标侧确认未写入","acknowledgeRisk":true}' \
  $E/v1/deliveries/<id>/replay
```

修改连接或任务必须带 `expectedRevision`（页面上的「版本号」）。不带或带旧版本
返回 409 `aborted`，意思是「别人改过了，刷新再来」——这是防止两个人同时编辑把对方
改动覆盖掉。

错误体统一是：

```json
{"code": "aborted", "message": "…", "details": null}
```

| HTTP | code | 什么情况 |
|---|---|---|
| 400 | `invalid_argument` | 参数/JSON 不合法 |
| 401 | `unauthenticated` | 没令牌、令牌无效 |
| 403 | `permission_denied` | 角色不允许 |
| 404 | `not_found` | 不存在**或不属于本租户**（跨租户一律 404，不泄露存在性） |
| 409 | `aborted` | 版本冲突 / 状态不允许 / 还有积压 / 需要确认风险 |
| 503 | `unavailable` | 数据库或依赖不可用 |

## 8. 常见问题

**Q：任务显示「转发中」，但投递记录里一条都没有。**
A：三种可能，按顺序查：① 源端 `northbound.enabled` 是 false；② 接入方式不是
`ingress_v1`（总览顶部会有警告条）；③ 任务的设备范围/数据类型过滤没命中。
先看总览的「等待投递」有没有涨——涨了说明源端在登记，问题在交接；一直是 0 说明
源端压根没登记。

**Q：目标说没收到，平台显示已送达。**
A：先看确认级别。如果是 `none`（MQTT QoS0），平台只保证「发出去了」，不保证
「对方收到了」，这不算 bug。如果是 `destination_acked`，平台拿到了目标的 2xx /
PUBACK，让目标那边按幂等键查日志。

**Q：能不能补发历史数据？**
A：首版不做历史补数。北向服务只处理**启用之后**新产生的数据。

**Q：能不能加第三方插件？**
A：首版不支持插件市场。连接器清单是发布方写死的两个官方插件（HTTP、MQTT），
不接受租户填任意 URL 进来。

**Q：改了任务配置，排队的数据会按新配置发吗？**
A：不会。投递行上钉着它生成时的任务版本，按**那一版**的规则发。新配置只影响
改完之后新产生的数据。

**Q：删除连接/任务会怎样？**
A：还有任务或未完成投递时，删除连接会被拒绝（409）。任务只有**草稿**能删——任务
一旦跑过，它就拥有了必须留存的投递记录，删除会毁掉审计证据，所以按钮只在草稿行
出现，后端也会用 409 拒绝。跑过的任务请用「停用」。
