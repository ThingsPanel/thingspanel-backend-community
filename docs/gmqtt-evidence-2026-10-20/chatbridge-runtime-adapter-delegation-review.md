# ChatBridge runtime adapter delegation fit — read-only review

Date: 2026-10-20. Reviewed the local ChatBridge checkout at `/Users/junhong/Downloads/code/chatbridge`. No source was changed; no environment secrets were read and no model was called. This is an interface fit check, not an authorization implementation or deployment proof.

## Minimal runtime hook

ChatBridge already has the necessary adapter lifecycle: `RuntimeAdapter.describe(installation, actor_context) -> ToolSurface` publishes `ToolSchema` entries; `authorize(installation, request_context, call)` returns `AuthorizationResult`; `execute(...)` returns `RuntimeResult`; and `validate_output(...)` validates the result envelope. `RuntimeDispatcher.dispatch` resolves the installed runtime, evaluates policy, calls adapter authorization, then execution and output validation. The clean extension point is a dedicated, fixed-origin broker-delegation runtime adapter registered in `RuntimeAdapterRegistry`, with a small fixed tool surface and server-owned owner client. It should not be a general HTTP adapter.

The Web/agent execution path constructs actor and request contexts on the server in `AgentToolExecutor`: actor context carries `tenant_id`, `actor_id`, and `thread_id`; request context carries the `ChannelBinding`, the same tenant/actor/thread values, and server-created callbacks. Model-controlled `RuntimeToolCall.arguments` are separate. A delegation grant can therefore be resolved and attached by the trusted server composition path as a private request-context value (or retrieved by an opaque server-side binding) before dispatch. The model schema and arguments must never contain the grant, parent JWT, URL, or authority selectors. `describe`/JSON schemas are presentation and are not argument enforcement by themselves: `RuntimeToolCall.arguments` is a generic dictionary, so the adapter's `authorize` must validate exact keys, operation, scope and argument bounds before any request.

## Existing Web identity path and gap

The Web UI obtains `/api/operations/v1/principal` with `credentials: 'same-origin'`, then uses the returned principal to construct `X-ChatBridge-*` actor/scope headers. The principal endpoint derives identity from gateway/OIDC headers or an explicitly configured loopback actor. ChatBridge explicitly documents that `read_web_actor` is a gateway adapter, not a JWT verifier: production must prevent clients from injecting those identity headers. The `/api/web/chat` handler calls this actor reader and passes tenant, system user, role, and a thread ID to the application. Application code namespaces a web thread by tenant and actor. This supplies a candidate trusted actor/thread binding only when the deployment gateway boundary is correctly configured.

The inspected Web UI source has the principal bootstrap but no call to `/api/web/chat`, and no current grant issuance, revocation, or server-side grant-to-thread binding flow was found. The current principal JSON is actor context, not an authenticated ChatBridge session credential. A future issuer should derive actor/tenant only from the verified gateway/session boundary, store a bounded opaque grant server-side, and make it available to runtime execution only through the server-created request context. The existing thread ID is a routing key, not sufficient proof of user authorization on its own. Do not return the opaque value to the model or place it in prompt, tool result, traces, or logs.

## Scope and limits

The adapter registry and `authorize`/`execute` hooks are sufficient for a narrow delegation adapter, but the current code does not itself issue or bind broker grants. Existing capability HTTP clients use fixed application endpoints; no generic arbitrary-URL HTTP runtime adapter was found in `runtime/adapters`. A `http_tool` enum exists in the skill-spec model, but no runtime adapter implementation was found by source search, so it is not evidence of an available safe tool. Before enabling delegation, add a server-only grant issuer/binding and current-session revalidation, explicit fixed operation schemas, strict argument validation, fixed endpoint allowlisting, and result/error redaction; otherwise fail closed. No ChatBridge, live gateway session, or ThingsPanel tool-delegation behavior was exercised here.
