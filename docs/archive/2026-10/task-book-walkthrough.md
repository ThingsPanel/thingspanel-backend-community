## 二、未完成的 16 项（A19–A34）

每项写三段：**干什么** / **为什么必须有** / **现状与判断**。

### A19｜设备模板关联、新设备继承、参数覆盖

- **干什么**：在设备模板里配一次规则，新设备自动继承；单台设备要特殊阈值时只覆盖参数，并能看到"我来自哪个模板"。绑定要存固定版本、参数、来源，`self` 引用在设备实例化时才解析。
- **为什么必须有**：这是**现有功能**，不是新增。老版本就支持"模板里配联动，新设备自动生效"，重写如果丢了它，客户会觉得升级后功能退步。
- **现状与判断**：`auto_bindings` 表在 A04 就建好（`binding_key` 唯一、带 revision/params/source/device_config_id），但**至今没有一行代码写过它**。A18 的"来源"是"这条规则来自哪个模板"，A19 要的是"这条规则绑到哪些设备"——一规则一来源 vs 一规则多绑定，必须两张表。**必须做，且是第一优先。**

### A20｜换模板、升级、删除、引用失效

- **干什么**：设备换模板、删设备、模板升级之后，旧规则不能偷偷继续跑。要能说清"哪些配置受影响、哪些任务停止"，并保留 tombstone 与身份映射。
- **为什么必须有**：A19 一旦有了"绑定"，就必然有"绑定指向的东西没了"。没有 A20，删掉的设备还会被 timer 唤醒，换模板后旧阈值还在生效——这是最容易被客户当成"系统乱来"的一类问题。
- **现状与判断**：A20 是 A19 的必然配套，不能拆开验收。完成标准里"无幽灵 timer"这条尤其重要。

### A21｜模板资源包的规则依赖与导入恢复

- **干什么**：导出设备模板时，把相关规则、场景、告警策略的版本和 hash 一起带走；换环境导入时重新映射设备与通知引用，重复导入不重复建资源，失败不显示成功。
- **为什么必须有**：这是现有"设备模板包/看板包"能力的延伸。客户做现场交付就是靠导出导入，如果规则不在包里，导过去就是一堆失效配置。
- **现状与判断**：依赖 A18/A19/A20。包里**不能**带凭据、真实接收人、运行记录、活动告警——这条边界要写进实现。

### A22｜改造共享联动与场景表单，保持原使用习惯

- **干什么**：用户还在原来的"场景联动/场景管理"里操作。需要时才展开持续时间、重复触发、分支、批量目标；保存后能给一句人话摘要。
- **为什么必须有**：后端全做对了，前端如果换了菜单和交互，等于让客户重新学一遍。任务书 1.1 节把"用户体验保留"列为硬约束。
- **现状与判断**：这是**前端任务**，源码在 `thingspanel-frontend-community`，当前工作树只有后端。需要单独开前端工作树；后端已备好接口（A04/A08/A11/A12/A13/A14/A18 全部就绪）。

### A23｜设备页、设备模板页、告警页的上下文接通

- **干什么**：从设备详情、设备模板、告警页进去，都能看到"真正对这个对象生效的规则"，改的是同一份配置。
- **为什么必须有**：同一个规则在三个页面显示不一致，是最常见的"客服说不清"来源。任务书要求"不增加重复编辑源"。
- **现状与判断**：前端任务，依赖 A19/A20 的绑定关系才有"模板来源/覆盖值"可显示。**排在 A19/A20 之后。**

### A24｜客户能看懂的执行详情与排障入口

- **干什么**：点开规则能看到"为什么没触发""执行到哪一步"；失败、未知、部分成功用人话解释；能跳到设备命令、告警、通知的详情。
- **为什么必须有**：这是任务书里 U01–U09 那套用户验收的落点。没有这个页面，A17 的六值解释只有开发能看懂。
- **现状与判断**：后端解释接口已有（A17），运行/步骤记录已有（A09）。剩下的是页面 + 时间线聚合接口。

### A25｜无副作用模拟与变更预览

- **干什么**：保存前用样本看看规则会怎么判；大范围改动能提前看到影响哪些设备。模拟绝不真的开关设备、发通知。
- **为什么必须有**：现在改一条影响 200 台设备的规则，客户只能"改完看结果"。而且模拟和真实运行必须走**同一套判定**，否则模拟说会触发、实际不触发。
- **现状与判断**：A17 已经复用同一个 `domain.Evaluate`，模拟可以接在这条线上；关键是把动作 adapter 强制换成无副作用出口。依赖 A19 才有"影响范围"可算。

### A26｜扩展现有 tpctl 命令行

- **干什么**：开发、实施、AI 用命令行创建、校验、模拟、运行、取消、解释、查告警，全部走同一应用服务。
- **为什么必须有**：现场实施和自动化测试都靠 CLI；如果 CLI 还连旧接口，等于留了第二套业务实现。
- **现状与判断**：依赖 A04/A17/A25。要有稳定 JSON、退出码、结构化字段错误，不能让人解析中文提示。

### A27｜业务 MCP 薄适配

- **干什么**：AI 能按用户意图帮忙配置和排查，但受和网页一样的权限限制；信息不足时返回明确错误，不自己编参数。
- **为什么必须有**：这是本轮"AI 使用"的交付项。重点是**工具注解不是授权**——租户必须来自可信会话，不能由参数决定。
- **现状与判断**：依赖 A26。和 CLI 共用同一批任务级工具，不新建独立 AI 业务核心。

### A28｜外部执行器统一输入输出合同

- **干什么**：以后专家用 Node-RED、大客户用 Flink，也从同一套入口拿事件、提交动作意图和告警判定。平台仍知道"谁执行、控了哪些设备、结果是什么"，并校验 scope、revision、epoch/seq、有效期、幂等、因果链。
- **为什么必须有**：这是**准入合同**。没有它，外部引擎只能旁路 MQTT 或直接改库，平台就失去了"谁动了设备"的追溯能力。
- **现状与判断**：A10 的代际/幂等、A15 的策略 revision、A16 的通知四态已经把合同需要的字段备齐。**这是真正的必做项。**

### A29｜Node-RED 与 Flink 最小接入样例

- **干什么**：一个 Node-RED flow + 一个固定版本的最小 Flink job/connector，各做一次独立冒烟（正常、重试/恢复、旧版本输出被拒），证明 A28 的合同真能接上。
- **为什么必须有**：**它是 A28 的验收手段，不是给客户装的东西。** 只写合同不做样例，就是任务书最忌讳的"文档里画了一条线"。
- **现状与判断**：**要做，但只做最小**。任务书明确"不要求社区版默认部署这些引擎"；也明确"如果只完成 mock，只能标合同通过、引擎未联调，不得按完成交付"。所以它不能砍，但可以排在 A28 之后、A31 之前。

### A30｜适配 App、面板、ThingsVis 和旧调用方

- **干什么**：网页改好了不算完。手机入口、面板上的场景按钮、告警详情链接、旧 API 调用方都要继续能用；无法同步升级的给有期限的薄兼容层，并登记退出条件。
- **为什么必须有**：这是"旧功能不丢"的最后一道闸。客户往往是从 App 或面板发现问题，那时已经上线了。
- **现状与判断**：依赖 A01 的消费者台账。难点是区分"没找到调用"和"已证明没有调用"——前者不能当作可以删。

### A31｜可恢复迁移、对账与回退工具

- **干什么**：老客户升级时，旧规则、场景、模板关联、告警历史能对上；迁到一半失败能继续；重跑迁移不会把已发出的控制和通知再发一次。流程是：去敏盘点 → dry-run → 影子评估 → 冻结旧执行取一致检查点 → 导入活动告警/pending/timer/绑定 → 对账 → 激活新代际。
- **为什么必须有**：没有它，这次重写只能在新装环境交付，老客户升不上来。
- **现状与判断**：依赖面最广（A01/A04/A08/A09/A15/A16/A19/A20/A21/A30）。核心难点是"状态迁移必须先于激活"，以及"回退不等于撤回已经发生的物理动作"。

### A32｜性能、容量、配额与数据保留

- **干什么**：设备多了、同时到期多了，系统表现可预期。压测前先冻结数字预算，报告要写清机器、负载、p50/p95/p99、积压、失败/unknown/拒绝、日增长。
- **为什么必须有**：任务书把性能本身当交付物，不接受"压测通过"这种结论。而且配额（租户/scope 队列、目标数、步骤数、调用深度、重试、保留、模拟预算）是防止一个租户拖垮全场的手段。
- **现状与判断**：结构上已经做了准备（主键单行查代际、批量复核、`LIMIT 1 + SKIP LOCKED` 推进），但**没有真实压测数字**。这块要起负载环境，工作量不小。

### A33｜旧功能、故障与真实部署验收

- **干什么**：跑 A01 全量功能对照、U01–U09 用户验收、V01–V32 故障矩阵；用**同一组发布构建产物**测新装、旧版升级、gateway/CORS、动态菜单、worker、migration、readiness 与恢复。
- **为什么必须有**：这是"测试完成"和"能交付"之间的分界线。现在 269 个自动化用例是单元/集成级，不等于真实部署验收。
- **现状与判断**：依赖一大片（A01/A07/A08/A11/A14/A16/A21/A24/A25/A26/A27/A29/A30/A31/A32）。故障矩阵里重启、断网、重复消息、旧任务晚到、部分设备失败是重点。

### A34｜切换单一执行路径并完成交接

- **干什么**：按演练过的步骤切换，确认旧引擎不再偷偷执行；记录激活版本、输入游标、在途结果归属；在兼容调用与旧待办清干净后删旧执行器和临时路径；交付安装升级、运维恢复、模板使用、CLI/MCP、外部样例、客服排障说明。
- **为什么必须有**：这是收尾。停旧执行器、迁状态、停兼容 API 是**三个不同时间点**，不能一个开关粗暴处理。
- **现状与判断**：依赖 A31/A33。现在不能动，因为旧引擎还在跑，接上就是双写。

## 三、几个容易误判的点

1. **A29 不是"给客户装 Node-RED/Flink"**。它是 A28 的验证手段，两个小样例 + 一次冒烟，社区版默认部署不增加任何服务。
2. **A21（资源包）、A30（App/面板适配）看着像外围，其实是"旧功能不丢"的必保项**，不能因为"主流程能跑"就跳过。
3. **A22/A23/A24 是前端任务**，源码在 `thingspanel-frontend-community`，当前后端工作树里做不了，需要单独开前端工作树。
4. **A32/A33 不是"最后补一下"**，它们的工作量在整轮里占比很高，尤其 A32 要起真实负载环境。
5. **A19 是当前第一优先**，因为 `auto_bindings` 表已经建好却没人写——这意味着"设备模板继承"这个现有功能现在是断的。
