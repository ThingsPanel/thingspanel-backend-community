**告警的 8 条业务规则**（验收时按这个问）：

1. 一个异常一个告警 —— 约束做在数据库上，不靠代码自觉。
2. 确认 ≠ 恢复 —— 确认只写 `acked_at`，`state` 仍是 `active`。
3. 不猜 —— 读不到数据判"未知"，不当成"恢复"（旧系统 D1 缺陷）。
4. 恢复要有依据 —— 没配恢复条件就保持活动，不自动恢复（旧系统 D5 缺陷）。
5. 改配置不打扰在跑的告警 —— 发新版本不清、不重复，只换判定依据。
6. 告警和通知同一事务 —— 不会"告警有了通知丢了"；通知发不出去告警仍在。
7. 两条入口分开 —— 检测型 / 事件型；事件型默认关闭且要白名单；重复事件只生效一次；同 ID 不同内容判冲突。
8. 等级 `H/M/L`，状态只有"活动/已恢复"。旧库 `alarm_status` 是 `L/M/H/N` 不是 `Y/N`。

**5.1 / 5.5 返回什么**（`DeviceAutomationResponse`）：

```
device_id
device_config_id          # 该设备属于哪个模板
rules[]:
  rule_id / rule_name / kind / enabled
  source                  # template | device | condition
  binding_id              # template/device 有，condition 没有

```

**为什么给一个端点而不是三个**：如果设备页分别调"模板规则""设备覆盖""条件匹配"三个接口，三个请求之间设备可能被改，页面就会同时显示三个不同时刻的答案。一个端点一次算完。

### 5.1 对接约定（设备 / 设备模板页必须遵守）

1. **响应是裸 JSON，不是 `{code, data}` 信封。** 自动化服务的 `/v1/*` 直接返回对象本身，不能走 `@/service/request` 那个统一封装。前端已有 `@/service/api/automation-rules.ts` 就是为这个写的，直接用它的 `call()`。
2. **错误带机器码。** 失败时看 `details.code`（如 `invalid_definition`、`binding_incompatible`、`directory_unavailable`）和 `details.fields[]`（每个字段一条），表单按 field 显示，不要只弹一句话。
3. **写操作必须带幂等键。** `POST /v1/rules/:id/bindings` 之类的写接口带 `request_id`，重试不会建第二条。前端 `automation-rules.ts` 的 `idempotencyKey` 已经处理。
4. **写入结果未知 ≠ 保存失败。** 连接在请求发出后断掉时，绑定可能已经建成。报"保存失败"会诱导用户再建一条。`AutomationApiError.outcomeUnknown` 就是给这个用的。
5. **不传 `tenant_id`。** 租户由调用方 token 决定，服务端不接受客户端指定的租户。
6. **目录不可用不要当成"没有规则"。** `GET /v1/device-automation/:deviceId` 在设备目录查不到时会返回 `issues[]` 里一条 `directory_unavailable`，此时 `rules[]` 里**设备级绑定仍然有效**，页面不能显示"这台设备没有自动化"。
7. **`source` 三个值要区分显示**：`template`（来自模板）、`device`（这台设备单独设的）、`condition`（旧式"条件匹配任意设备"的规则，没有绑定）。
8. **`overridden[]` 是"哪些参数被这台设备改过"**，不是"哪些参数有值"。全量生效值在 `effective`。

## 8. 菜单外：迁移与对账（A31 + 升级脚本，没有页面）

老客户升级时把旧库搬过来。不是菜单功能，但没有它就只能在新装环境交付。

### 8.1 一条命令：`cmd/auto-upgrade`

```
auto-upgrade --old-dsn "postgres://user:pass@host:5432/ThingsPanel?sslmode=disable" \
             --api http://127.0.0.1:4000 --token '<令牌>' \
             --dry-run=false
```

| 参数 | 作用 |
| --- | --- |
| `--old-dsn` | 旧库连接串（也认 `TP_OLD_DSN`），只读 |
| `--api` / `--token` | 新服务地址与令牌（也认 `TP_TOKEN`） |
| `--tenant` | 要迁移的租户；旧库只有一个租户时可省略 |
| `--dry-run` | 默认 `true`：只出计划不写库。确认后加 `--dry-run=false` |
| `--list-tenants` | 只盘点旧库里有哪些租户、各有多少对象 |
| `--batch` / `--limit` | 每批条数 / 每个 pass 最多处理多少条 |
| `-v` | 连成功和跳过的条目也打印 |

**两遍，顺序不是装饰：**

1. **第一遍**：`alarm_config` → 事件型告警策略。
2. **第二遍**：`scene_info` + `scene_automations` + 活动告警。

原因：场景/联动的"触发告警"动作、以及活动告警的领养，都要先有策略存在才能解析。
计划是快照的纯函数，所以"计划了但还没写入"的策略对第二遍不可见 —— 必须分两遍。
两遍都在同一条命令里跑完。

**读旧表的对应关系：**

| 旧表 | 用途 |
| --- | --- |
| `scene_info` + `scene_action_info` | 场景与有序动作 |
| `scene_automations` + `device_trigger_condition` + `action_info` | 联动、触发条件、动作 |
| `alarm_config` | 告警配置（只有名字/等级/通知组） |
| `latest_device_alarms` 或 `alarm_info` | 活动告警。有前者用前者（带设备 id）；只有后者时从 `content` 的 JSON 里取设备 id，取不到就交给计划器写"没有主体"，不猜 |
| `devices` / `device_configs` | 用来核对动作引用的目标还在不在 |

### 8.2 接口（脚本调的就是这五个）

| 端点 | 干什么 |
| --- | --- |
| `POST /v1/migrations` | 按快照生成计划（默认 dry-run，`apply=true` 顺带跑第一批） |
| `POST /v1/migrations/:id/apply` | 分批应用，可重复调用（重跑不重复建） |
| `GET /v1/migrations/:id` | 查这次迁移的全部条目与结论 |
| `POST /v1/migrations/:id/verify` | 对账：缺失 / 停用不一致 / 被改过 / 孤儿 / 重复活动告警 / 未解决 |
| `POST /v1/migrations/:id/rollback` | 回退，默认不删已执行过的规则（`force` 才删） |

代码：`migration_service.go`（5 个端点）、`migration_plan.go`（纯函数计划）、
`legacy/scene.go` + `legacy/automation.go`（转换规则）、`store/migration_store.go`、
`migrations/14`–`16`。用例：`a31_migration_test.go` 21 条 + `legacy/automation_test.go` 12 条。

**三条必须知道的语义：**

1. **计划存库不重算。** 应用的就是批准过的计划，不会在 apply 时重新读旧库，避免"批的时候一个样、跑的时候另一个样"。
2. **未解决项单独占一行、单独计数。** 所以 `applied + failed != total` 是正常的；能把客户真正会丢的东西显式列出来。
3. **回退不撤回已经发生的动作。** 执行过的规则默认保留（`kept`），因为它可能是"命令确实发出去过"的唯一记录；已确认过的告警同理。

**能自动转 / 不能自动转（这是当前真实结论）：**

| 旧对象 | 状态 | 原因 |
| --- | --- | --- |
| 场景 `scene_info` + `scene_action_info` | ✅ 转换 | 顺序、目标、告警动作都保留 |
| 联动 `scene_automations` + `device_trigger_condition` | ✅ 转换 | `group_id` 是 AND 组、组间 OR；运算符是字符串（`=` `!=` `>` `<` `>=` `<=` `between` `in`），旧引擎直接消费，原样搬过去 |
| 告警配置 `alarm_config` | ✅ 转成事件型策略 | 旧表没有触发条件列，由联动/场景或外部调用触发，所以只声明 `sources=[event]` + 允许的调用方（从引用它的联动/场景推出来） |
| 活动告警（`alarm_status` ≠ N，或 `processing_result=UND`） | ✅ 领养 | 不发通知，身份按 (策略, 主体, 维度) 去重；打开时间沿用旧时间 |
| 已恢复/已处理告警 | ✅ 跳过 | 导入会让客户已经处理掉的告警复活 |
| 停用的告警配置（`enabled=N`） | ✅ 跳过 | 迁成启用等于把客户关掉的东西又打开 |
| 时间范围触发（`trigger_condition_type=22`） | ⛔ 需人工 | 是"什么时候允许跑"，属于排程，不是触发组 |
| 服务型动作（`action_type=40`） | ⛔ 需人工 | 旧的是调 webhook，本版本没有承接方 |
| 状态条件用「全部」（`ALL`） | ⛔ 需人工 | 意思是"任意上下线变化"，新模型没有这个条件 |
| 事件字段级匹配 | ⛔ 需人工 | 旧 `trigger_value` 是匹配配置 JSON，要按字段重建 |
| 只激活别的场景、自己不碰设备的场景 | ⛔ 需人工 | 新模型要求规则有目标集，纯"激活场景"的规则没有目标 |
| 通知组 `notification_group_id` | ⚠️ 只提示 | 通知 owner 有自己的策略 id，写外来 id 会变成"看起来接了、其实不发" |
| 在途 pending / timer / 绑定 | ⛔ 不导入 | 旧引擎仍在执行，按任务书边界留在原 owner，切换时（A34）再处理 |
| `alarm_history` / `alarm_info` | ⛔ 不导入 | 是日志不是配置，留在旧表可查；报告里会打印条数 |

> **两处曾经写错的判断，已更正。**
> 早先这里写的是"旧 `trigger_operator` 是数字 1..8、社区版没有消费方"。事实相反：
> 运算符是字符串（`internal/model/device_trigger_condition.http.go`），
> 且 `broker_automation.go` / `automate_telemetry.go` 真的在读它并比较。
> 所以联动不是"无法核对"，是"能原样翻译"。上面那张表是按代码核对后的结论。
