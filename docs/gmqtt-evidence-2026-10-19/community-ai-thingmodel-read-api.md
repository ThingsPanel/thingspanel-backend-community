# Community AI ThingModel read API evidence (2026-10-20)

Read-only source review of `kernel-worktree` at commit `37fbb5e8e83c47fa98a1eea59fefa38ceff97737`; `git status --short` was empty before this evidence file was added. No source, database, service configuration, or credentials were changed or read. The goal is to ground `devices.describe` in the existing tenant-scoped device/template binding and immutable published ThingModel API, rather than an old projection or a second model store.

The legacy device-metadata service also has `/api/thing-models/:id/versions/:version`, but that returns legacy snapshot rows. The v2 repository deliberately filters to `canonical_snapshot=TRUE` and the model row must have a canonical model; migration 0015 explicitly leaves old rows unclassified until converted. Therefore a legacy template binding whose snapshot has not been explicitly converted may not resolve through the v2 API. Do not silently fall back to legacy model projections or treat a current draft as a published version. Evidence: `encore-api/devicemetadata/service.go:127-145`; `encore-api/devicemetadata/migrations/0015_native_model_commands.up.sql:1-3,15-32`; `encore-api/thingmodel/postgres.go:200-250`.

## Authorization and safe lookup sequence

All listed endpoints are declared `auth`. Device/template handlers derive tenant scope from `authn.CurrentData()` and query by that tenant. The v2 adapter additionally requires both authenticated subject and tenant, maps `TENANT_USER`/`TENANT_VIEWER` to read capability and admin roles to read/write/publish/delete, then the application checks `thingmodel.read` and queries by the same tenant. A request with a different tenant cannot use the supplied model ID to cross scope. Evidence: `devicemetadata/models.go:249-255`; `thingmodel/service.go:232-258`; `thingmodel/app/application.go:407-439`; `thingmodel/core/snapshot.go:15-28`.

For `devices.describe`, use one user-authorized, tenant-scoped flow: fetch the device; fetch its referenced template; take that template's `thing_model_id` and pinned `thing_model_snapshot_id`; list v2 versions for that model; select the entry whose `snapshotID` exactly equals the pinned snapshot ID; fetch that entry's `publishedRevision`; verify the response repeats the expected model and snapshot IDs; return semantic model fields and the nested pinned resource revision. If no exact snapshot match exists, report that this binding is not available in the canonical published API. Never substitute the model's latest published revision, draft, template label, cached projection, or current mutable resource document.

## Verification limits and gaps

The source contract is verified at the commit above. Read-only local HTTP probes found `GET /api/device-metadata/healthz` returned 200 on loopback port 4000, but `lsof` attributes that listener to OrbStack, so this does not identify a running `kernel-worktree` API. Ports 5000 and 7000 returned 403 for that unauthenticated health probe; no authenticated model/device query was made. Runtime API reachability and real tenant responses are therefore **not verified**.

There is no single API that returns the device, template binding, canonical published revision, and snapshot resources in one response: the caller must make the scoped lookups above. There is also no native device-level ThingModel binding in `Device`; binding lives on `DeviceTemplate`. The current authorization adapter derives v2 capabilities from JWT roles; whether the community AI should receive a human delegated token or a narrowly scoped service identity is a product authorization decision, not established by this API review. Legacy snapshots not converted to canonical v2 remain a known availability gap.
