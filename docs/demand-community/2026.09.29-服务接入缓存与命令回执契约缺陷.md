# 服务接入缓存缺陷与 connector 回执兼容性报告

## 修复前已核实的平台缺陷

三台服务接入设备在数据库中有 access_way=B 和有效 service_access_id，旧 Redis 设备 ID 键里两项却为 null，TTL=-1。修复前3cbd9c9e的路由实现会读取该缓存并把服务设备误判为原生 MQTT，丢失插件主题前缀。该现象证明缓存与数据库不一致及当前路由依赖不完整缓存；尚未确定旧记录写入者，不断言只是旧版本残留或其他进程覆盖。两条现场失败记录 f1e6356d-b543-bc83-a231-63dd59dd8c8d、b4212b70-14c4-2071-a259-b9f1f166d588 停在状态1。

## 已核实的格式不匹配，尚未认定正式契约责任

HA connector 用 {device_id, values:{result,message,ts}} 回执；当前平台支持直接 {result,message,ts} 和 values 为 base64 的旧信封，不支持 values 对象。EZVIZ/SRS 以及本项目通用开发模板也使用对象格式，但这些示例相同不能单独证明 ThingsPanel 正式契约要求接受对象。connector 可以先改成平台现有支持的直接 ACK，不必为此改平台解析器。

## 对正确插件主题命令的逐条核实

2026-09-29 13:27:48，ESP 命令 f3be966f-67f6-add0-fc38-d99499165322 的内容是 switch/off。平台实际发布到 plugin/homeassistant/devices/command/{number}/{message_id}，HA connector 日志有相同 message_id 的收包与 command handled，随后 HA state_changed 遥测为 off。ThingsPanel MCP 当前 ha_state 的值为 off，时间为13:27:48.159。因此该命令实际已生效，故障是执行回执记录未更新：平台收到同 message_id 的 result=0 对象信封后解码失败，日志仍为1且rsp_data为空。

13:31:05 的 f1e6356d-b543-bc83-a231-63dd59dd8c8d（ESP/on）和 b4212b70-14c4-2071-a259-b9f1f166d588（Yeelight/off）则实际发到原生 devices/command 主题。HA 没收到它们，不能与上述正确插件命令合并判定为同一种失败。

## 萤石的具体关系

Broker 日志确认上述13:31两条原生主题命令的 not bound 回执来自 local-ezviz-ezviz-cmd 客户端。它因订阅原生通配符收到了误投递的HA设备命令；这是误投递后的旁支结果。正确 plugin/homeassistant 命令的处理链没有萤石，不应把萤石作为HA专属主题命令失败原因。

## 处理边界与建议

HA 保持只订阅自己的插件主题，不增加原生主题兼容。此前原生订阅方案撤销。

对于回执格式，可只让HA connector发送当前平台支持的直接 JSON ACK {result,message,ts}，保留对应 message_id；不必改TP解析器。该变化修复执行记录，不会修复未送到插件的命令。

TP旧缓存与数据库不一致导致误路由的问题单独报告给平台维护方。历史代码确实有依据设备配置找到ServiceType=2服务插件前缀的路径，不能宣称TP以前不能控制服务设备；当前问题聚焦无设备配置设备与新的服务关系路由依赖不完整缓存。

独立HA仓库提交25bc297（2026-06-18）曾移除原生订阅，保留插件主题；该Git日期不能直接当作现场故障首次出现时间。examples目录是独立仓库的符号链接，查历史需进入真实仓库。

本轮TP生产代码改动已撤回，未提交、未部署；此前3cbd9c9e保留。本次核实仅只读查询，没有向灯发新命令或修改connector。

## 历史与回执处理是否导致误路由（本轮代码核对）

- git blame 显示设备ID缓存“JSON解码成功即采用、写入TTL=0”核心逻辑来自2024-06-06的0ac9305a；这是代码存在时间，不能据此确定现场缺字段缓存的生成时间或写入者。
- 2025-10-22的2ed5ab3a增加无设备配置时按MQTT处理，插件前缀仅在非MQTT且存在device_config_id时查找。该路径没有通过service_access_id解析无模板服务设备；不能将这次提交日期直接认定为现场HA故障开始日期。
- 2026-09-29 12:59:40的3cbd9c9e同时新增服务关系路由和命令回执处理。新路由依赖缓存里的access_way/service_access_id，却未处理缺字段缓存，导致此次修复未稳定生效；修复遗漏在路由所用设备信息的可靠性，不在回执逻辑。
- 回执新增代码没有修改设备缓存写入或主题选择。现场HA对象回执在subscriber.go:75解码、83-88返回，未执行100行读取缓存，因此不能把这条回执错误归因为缓存覆盖。
- TP publicPayload.Values=[]byte的定义可追溯到2025-10-15的4e6f79f1，今天修改前的verifyPayload也会拒绝values对象。HA对象回执当前这一行来自2026-06-18的851f63e；不能说对象格式不兼容是今天新引入的，今天扩展直接ACK仍漏了该格式。

HA收命令和调用设备已有成功证据，订阅无需改；回执格式兼容仍待处理，不应概括为HA侧完全不用管。此前用户记忆中的正常控制还需核对当时设备模板/调用入口/部署版本，现有证据不足以复原其具体链路。

1. TP命令、属性设置、遥测控制入口都改从dal.GetDeviceByID读取数据库完整设备关系；属性获取原先已读DB。下行不再靠共享设备缓存判断服务归属。服务前缀仍通过服务接入与服务插件配置解析，无HA专用分支。全局Redis键、上行读取和网关父查询保持原逻辑。

### 实机结果（2026-09-29 14:26–14:29 +08）

从ThingsPanel MCP通用send_device_command入口对tenant-ha三台无模板灯做两轮开关，12条控制均成功。每条记录都发布到plugin/homeassistant主题、HA日志收到同message_id、ACK result=0入库status=3；每轮结束直接GET HA实体状态确认on/off，并通过MCP遥测确认上行状态。

### 收益、范围和权衡

无模板服务命令不再被缺字段缓存误路由，成功与失败回执可记录，发布结果不会覆盖早到命令回执。每次相关下行增加一次设备DB查询；尚未做吞吐量压测，不声称性能无影响。缓存其他用途和历史记录不回填。服务归属解析失败时停止发送；既有非服务非MQTT前缀解析失败的警告逻辑未在本次修改，不能泛称全平台所有失败路径都已闭合。

推荐保留本次最小通用修复。若未来压测证明设备查询成本明显，再设计专用带版本及失效机制的路由缓存；仅清缓存不能防止再次出现缺字段，也不建议通过让HA订阅原生主题绕过平台路由。
