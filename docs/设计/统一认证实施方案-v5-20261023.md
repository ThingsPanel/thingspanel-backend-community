# ThingsPanel 统一认证实施方案 v5

日期：2026-10-23。状态：已实现首轮代码并完成隔离验证；真实企业来源和微信真机验收待配置。

目标：保留原用户、租户、设备和权限，让原账号登录、企业登录与微信小程序登录进入同一身份及会话体系。以安全边界、真实终端可用、迁移风险和维护成本作为选择依据，不承诺抽象的“全局最优”。

本文承接用户提供的《ThingsPanel认证设计-v4》。v4 的统一 Encore、保留原账号、显式绑定、单会话所有者原则继续有效；本文调整当前基线、小程序完整客户端范围、上游身份合并防护及紧急撤销要求。原始资料不覆盖。下面的参数和接口是实施合同，不代表现有系统已具备。

## 1. 本期交付

| 能力 | 决定 | 验收边界 |

## 3. 为什么选择这个结构

| 选项 | 优点 | 成本或风险 | 结论 |
| --- | --- | --- | --- |
| 每个登录渠道直接接到业务后端 | 第一个渠道代码较少 | 每个渠道重复验证、绑定、撤销和审计；企业来源继续扩张 | 不采用为总体架构 |
| 统一把原用户和权限迁入外部 IAM | 身份管理集中 | 原 ID、租户资产、角色及历史客户端迁移范围显著扩大 | 本期不采用 |
| 统一 authn + 标准 OIDC / 微信直连适配器，保留原账号和会话 | 不要求新部署 IAM；渠道只负责身份证明 | OIDC 来源仍需独立安全验收 | 采用 |
| Casdoor 等身份代理 | 统一管理多个来源 | 新增运维及上游合并风险 | 按需接入，非必装 |

根据用户确认“尚未部署 Casdoor”，本期消除其必装依赖：企业直接配置标准 OIDC；微信小程序由服务端调用官方 code2Session。未来 Casdoor、Keycloak 等作为可选 OIDC 来源，共用绑定、会话和撤销逻辑。

统一链路：外部身份验证 → 显式映射原 UserID → 本地账号/租户/登录方式准入 → 原平台会话 → 同一身份上下文 → 原业务权限。

认证方式只回答“你是谁”，不能授予租户成员资格或把外部管理员组直接映射为平台超管。人员、API Key、通知插件/服务凭据明确区分，机器身份不能绑定人员账号。

## 4. 账号绑定与上游信任

1. 外部身份使用精确可信 issuer 与稳定 subject；绑定表对这两个字段施加全局唯一约束。一个外部身份只属于一个原用户，一个原用户可以有多个身份。client/application、来源和可信配置版本另外记录并检查，不能通过换 client 绕过身份唯一性。
2. 不根据邮箱、手机号、昵称、UnionID 自动认领原账号；不创建假邮箱、默认密码或默认管理员。
3. 未绑定的外部身份只得到 `binding_required`，不得到平台会话。界面引导原账号登录，再明确确认绑定。
4. 绑定需要仍有效的人员会话、原账号再次验密和新鲜外部身份证明；只调用验密能力，不调用会签发会话的完整 Login。完成时再检查用户状态及会话。
5. 同用户重复绑定幂等；跨用户并发由数据库约束拒绝，不能覆盖原归属。绑定成功不重签平台会话，不踢掉正在操作的会话。
6. 使用 OIDC 时必须同时验证身份源上游层（包括可选 Casdoor）：注册、身份连接、账户恢复、邮箱验证及管理员修改都不能把攻击者身份自动并入已经映射的 subject。检查具体固定版本的配置和代码，不能仅依赖一个“关闭自动绑定”的假定开关。
7. 在隔离测试组织中验证同邮箱、大小写用户名、同手机号、跨 provider、删除重建及恢复账号场景；不能安全隔离的来源不上线。Casdoor 管理员对 subject 的控制属于明确的运维信任边界，应最小授权并审计。

Casdoor 官方文档描述了按 OAuth 身份、启用的邮箱/手机号及用户名匹配的自动连接机制，因此平台侧显式绑定本身不够：[OAuth provider overview](https://casdoor.ai/docs/provider/oauth/overview/)。

## 5. 会话、撤销和多终端

- 唯一 authn 拥有平台凭据签发、续期、撤销和准入；沿用原用户和 Redis 会话，不建立另一套永久会话中心。原生接管后不再通过 Gin 登录/详情接口验证身份。
- 每次鉴权校验签名、固定算法、必需且未过期的 exp、实际会话存在、账号状态、租户和角色一致性。角色显式白名单映射；未知角色拒绝。状态库故障拒绝访问并返回依赖故障，不能降级为 dev/passthrough。
- 保留已有“允许共享账号/单登”配置：多终端模式允许同账号多个独立会话；单登模式替换旧会话及其通知资格。并发签发与撤销必须原子化，不能把多终端误做多个平台用户。
- “退出当前设备”撤销当前会话及其通知资格；管理员紧急处理需要能撤销该用户全部会话。账号停用后，后续请求拒绝，后续通知目标解析排除该账号。已经被外部推送服务接收的消息无法保证撤回。
- 外部绑定停用保留审计记录与唯一性，不直接删除后允许他人抢绑；重新绑定必须重新验证双方身份，并验证原归属处理权限。

**紧急撤销的最小实现决策**：本期允许停用一个外部绑定时同时撤销该用户全部平台会话，避免为了精准按来源撤销引入第二账本。在原用户记录增加认证版本，签发时把版本写入平台 JWT，鉴权与通知资格验证都检查当前版本；不匹配即拒绝。版本更新是账号迁移 owner 的增量变更。旧 token 无版本仅在迁移兼容期且账号从未发生版本变更时可按初始版本处理。回滚到不识别版本的程序前必须清空受影响会话并强制重新登录，不能恢复旧 Redis 快照使撤销失效。

这是新增实现要求，尚未落库或编码。绑定停用与账号版本递增需要同数据库事务；通知发送前也必须检查版本/账号准入，不能只等 Redis TTL。租户管理员仅能处理其有管理权限的人员；超管操作单独审计。

本期定位为“支持企业身份登录”。如果企业要求离职自动禁用、禁止本地密码绕过、强制企业 MFA，必须另外交付来源准入策略、生命周期同步和对应 SLA；不能凭一次 OIDC 登录就称为完整企业身份治理。平台超管本期默认不开放个人微信登录，保留受控管理入口；外部身份登录不得降低已有 MFA 要求。

## 6. Web 与小程序协议

Web 沿用 v4 的 providers/start/callback/exchange 及 bind/start、bind/complete 接口职责。使用授权码、PKCE S256、state/nonce；服务端严格验证可信 issuer、audience、签名、允许算法、有效期和事务。回调只能访问已登记地址，站内返回地址拒绝协议相对 URL、编码绕过和任意外链。参考 [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)。

实施默认值（产品选择，不是标准规定）：

| 对象 | 默认与约束 |
| --- | --- |
| 登录/绑定事务 | 5 分钟；login/bind 用途隔离；保存来源、client、配置版本及发起方关联 |
| 一次性交换票据 | 60 秒；只保存摘要；原子领取；消费后失败重新开始，不恢复票据 |
| 绑定验密证明 | 最长 5 分钟且不超过原会话寿命；绑定原用户、原会话及当前事务 |
| Web 临时 Cookie | HttpOnly、Secure、SameSite=Lax；采用顶层 GET 回调；不把单个 state 放 Cookie 导致多标签互相覆盖 |
| 多标签 | 稳定短期浏览器关联加独立事务；一个标签完成不能消费另一个标签的事务 |
| 身份时间容差 | 默认 60 秒；验证测试覆盖边界，不把容差用来放宽平台会话撤销 |
| 认证响应 | no-store；回调 no-referrer；token 不进 URL；票据交换后清理地址 |

按来源、IP 和账号分别限流，错误验密复用现有锁定规则；具体阈值在基线调查后结合现有配置与代理真实 IP 信任链确定。不要仅按 IP 锁住整个企业出口。固定 JWKS 来源，不跟随 token 提供的 jku；未知 kid 的受限刷新、并发合并、超时及密钥紧急撤销纳入测试。敏感字段必须验证 Encore trace、代理日志和错误日志，而不只是应用日志。

小程序接口：

- `POST /api/v1/auth/wechat-mini/login`：接收临时 code 与服务端登记的应用别名，返回现有平台登录结构或稳定的 `binding_required` 状态。
- `POST /api/v1/auth/wechat-mini/bind`：有效人员会话、再次验密与新的微信 code；返回绑定结果，不签新会话。
- 应用别名只能映射服务端固定配置；不接收客户端给定的 issuer、换码 URL、Secret 或目标 UserID。
- code 不持久化到客户端 storage；服务端以摘要按应用隔离并跨 login/bind 用途原子领取，防止重复使用。超时后获取新 code，不重试消费旧 code。
- 小程序直接调用微信固定 HTTPS code2Session 端点；AppSecret 仅在服务端私密配置，客户端只发送临时 code。以 AppID 派生 issuer、OpenID 作为 subject，忽略 UnionID，不返回或持久化 session_key。网站扫码另作适配；不机械套用网页 PKCE/nonce 流程。

接口参考：[微信 code2Session](https://developers.weixin.qq.com/miniprogram/dev/api-backend/open-api/login/auth.code2Session.html)。当前官方文档抓取失败，代码依赖的 GET 参数和错误响应已用协议夹具验证，仍须真机核实，不能替代真实来源验收。

## 7. 客户端交互与兼容

登录页只显示已配置且适用于当前终端的入口。小程序显示“微信登录”和“账号密码登录”；首次微信未绑定进入“登录已有账号并绑定微信”，展示来源及待绑定账号，允许取消。不能强制索取头像、昵称或手机号作为登录前提。

复用现有登录状态恢复、用户详情、菜单及权限初始化；详情失败不进入伪登录状态。401 清理失效会话，403 保留会话并提示无权限，503 保留可能有效的会话供重试。切换服务器先清除原服务器身份与临时绑定状态，不能把旧 token 或绑定事务发送到新服务器。

对外保留必要 v1 `code/message/data`、登录 `token/expires_in`；不发明 refreshToken。规范退出为 POST `/api/v1/auth/logout`，旧 GET 退出在登记消费者后暂时兼容，两者共用撤销逻辑。Bearer 为规范，迁移期间兼容 x-token，两者同时出现必须一致。Encore 前置鉴权错误采用框架错误，认证适配层处理，不做全站请求重构。

现有原生 App 的 CID 注册、账号切换及退出流程继续工作；小程序不走原生 App 的 CID 注册。UI 使用现有组件和文案风格，仅增加必要入口和绑定确认，不重做业务页面。

## 8. 实施顺序和发布门槛

| 阶段 | 必须交付 | 通过才可进入 |
| --- | --- | --- |
| P0 基线与技术验证 | 唯一 Encore 集成基线；账号 schema/Redis/migration owner；路由和会话 writer 清单；若采用身份代理则固定镜像版本与摘要；隔离测试上游合并、真实企业和小程序身份合同 | 依赖事实清楚，小程序方案可验证；缺真实凭据时标记该来源阻塞 |
| P1 原账号会话统一 | 原生验密/锁定/初始化/签发/续期/撤销/状态；通知适配；认证版本；停用绑定及审计所需公共能力 | 原账号回归通过；隔离认证到 Gin 的 HTTP 访问仍正常；无双 writer |
| P2 企业来源与绑定 | OIDC 事务、可信身份校验、唯一绑定、安全配置、最小 Web 流程 | 负面测试和至少一个真实企业来源闭环 |
| P3 小程序完整交付 | 两个接口、现有客户端统一入口、绑定/取消/错误恢复、清除遗留分叉 | 真机新用户未绑定、原账号绑定、再次登录、冻结和退出通过 |
| P4 发布与交接 | 增量迁移、新装/升级/回退演练、日志检查、前后端版本清单及来源验收记录 | 每项证据齐全才启用对应来源 |

允许先实现不依赖真实凭据的模块，但真实来源验收不得由 mock 替代。配置需要小程序 AppSecret、合法 HTTPS 域名、测试人员及一个真实企业 IdP；Secret 放私密配置，不能写文档或聊天。未完成所选 OIDC 来源安全核验前，不启用该入口。无需为微信单独部署 Casdoor。

## 9. 关键验收用例

| 类别 | 必须证明 |
| --- | --- |
| 原账号兼容 | 原 ID/密码哈希/租户/设备不变；密码、RSA/salt、锁定、首次初始化、必要刷新与恢复入口按清单验证 |
| 协议攻击 | 错 issuer/audience/签名/算法/nonce/state、过期、PKCE 不匹配、回调重放、票据并发只消费一次 |
| 账号接管 | 同邮箱/手机号/用户名不能经 Casdoor 自动并到已绑定身份；跨用户抢绑拒绝；机器凭据不能绑定 |
| 本地权限 | 两租户与不同角色无越权；外部管理员不能提升本地权限；来源/application 更换不能混用 |
| 会话 | 并发退出/续期、单登替换、多终端、冻结、版本撤销、Redis 故障均按契约处理；旧路径不能复活会话 |
| 紧急处理 | 停用绑定与版本递增一致；旧会话拒绝；审计可追溯；回退不得让撤销失效 |
| 小程序 | 真 code、错 code、重放、错 AppID、未绑定、同一原账号登录、取消及失败恢复；测试和真机证据分开 |
| App 通知 | 同账号两台手机按共享设置收到通知；退出一台后后续目标只含有效设备；换账号不串推；冻结/全会话撤销不继续解析旧设备 |
| 可运维性 | 外部故障不拖垮原账号入口；代理/trace/日志无凭据；未知 kid 刷新不形成无限外部请求 |
| 发布 | 空库初始化、现有库增量升级、重复执行、失败回退、旧客户端兼容；独立检出构建无需相邻仓库 |

测试报告逐项记录提交号、镜像摘要、配置摘要（不含秘密）、命令/步骤、预期、结果和脱敏证据。状态只能是通过、失败、未执行或受阻，不能以健康检查、拿到 token 或旧测试报告填“完成”。

## 10. 迁移与回退

先做可回退的增量 schema，保留旧账号字段；绑定表和认证版本由账号 schema 唯一迁移 owner 管理。旧 Gin 业务不整体重写，但必须登记所有登录、初始化、注册、刷新、切换用户、会话续期及推送资格消费者。每条切换路由只有一个 writer；当前仍存在的 Gin 续期不能在 Encore 接管后继续写。

发布前隔离认证到 Gin 的访问做闭环实验；不能以关闭一个请求函数就宣称所有通知/旧业务鉴权已统一。无法覆盖的路径列出影响，并阻止依赖该路径的闭环发布。

回退保留新增绑定/审计数据，不执行破坏性 down。停用新外部入口，撤销新会话，确认旧版本能执行同等撤销和准入规则后才切回；不兼容时采用受控维护及全部重新登录，不能放回会绕过认证版本的旧服务继续对外。真实来源分开启用，验收未通过的入口不展示。
