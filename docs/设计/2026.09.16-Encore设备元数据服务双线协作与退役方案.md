# Encore 设备元数据服务双线协作与退役方案

**状态：协作/退役流程待执行；本机共享运行时已落地。本文件是团队协作与收工准则，不是一次线上切换指令。**

**日期：2026-09-16**
**适用仓库：** `thingspanel-backend-community`、`thingspanel-frontend-community`、`iot-api-encore-kernel`

## 1. 已确认的决策

1. 社区版继续作为稳定发布线：保留设备接入、MQTT、遥测、存储、现有设备控制和既有客户 API。
2. Encore 的 `devicemetadata` 是设备元数据的新事实源：负责物模型、不可变版本快照、设备/模板绑定、能力查询、命令标识符和 onboarding。
3. 要退役的是**旧物模型/设备元数据的事实源及其旧兼容实现**，不是整个社区版后端。
4. 在满足本文的退役门槛前，旧路径只作为可观测、可回退的兼容层；不得同时把两个数据库当作可写事实源。

因此答案是：**可以最终只保留新的 Encore 设备元数据服务，但必须让社区版继续作为数据面和发布产品的一部分。** 若删除社区版的 MQTT、遥测或现有控制链路，就不再是“元数据替换”，而是一次高风险的全平台重写，不在本方案范围内。

```text
                          ┌────────────────────────────────────┐
稳定发布线                │ ThingsPanel Community              │
前端 ────────────────>    │ 接入 / MQTT / 遥测 / 存储 / 执行命令 │
                          └───────────────┬────────────────────┘
                                          │ 只读能力投影、命令委派
                                          ▼
新增能力线                ┌────────────────────────────────────┐
Encore devicemetadata ──> │ 物模型 / 快照 / 绑定 / 能力 / 审计   │
                          └────────────────────────────────────┘
                                  唯一元数据事实源
```

## 2. 当前资产及处理方式

| 资产 | 当前判断 | 收工处理 |
|---|---|---|
| 社区后端 `main` | 跟随官方主线，承担稳定发布 | 继续维护和发版；不再承载新的物模型领域逻辑 |
| 社区后端旧 `thingmodel` 分支 | 早期兼容 POC，落后主线较多 | 冻结、打 tag、保留为参考；不直接 merge/rebase 到 `main` |
| 社区前端旧 `thingmodel` 分支 | 有页面、测试和交互资产，但基线过旧 | 冻结；按当前 `master` 重建必要页面和 API 调用 |
| Encore `devicemetadata` | 已有版本、迁移、回滚、custom control、onboarding 等能力 | 继续作为唯一的新元数据开发线；先补齐验证和发布纪律 |
| 旧的模板/设备绑定字段 | 迁移期可读取 | 迁移完成后只读归档，最终移除旧代码读取，不立即删除历史数据 |

## 3. 团队协作模型

### 3.1 不是“大家都切本地分支”就够了

每个人确实都应在本地独立分支开发，但分支必须推送到远端并通过 Pull Request 合并。否则同事之间只能靠拷贝目录或口头同步，冲突会在最后集中爆发。

建议每人一个工作目录或 Git worktree，避免为了在两个版本间切换而污染工作区：

```bash
# 在各自克隆的仓库中执行；示例分支名按团队规范替换
git fetch origin --prune
git worktree add ../tp-encore-metadata-alice -b feature/encore-metadata-alice origin/main
git worktree add ../tp-community-hotfix-bob -b feature/community-hotfix-bob origin/main
```

同一位开发者需要同时改 Encore、社区后端和前端时，使用三个独立 worktree；不要在一个目录里反复 `checkout`，更不要带着未提交改动切分支。

### 3.2 分支和合并规则

| 分支 | 用途 | 权限与生命周期 |
|---|---|---|
| `main` / `master` | 各仓库的日常集成线 | 受保护；只能经 PR 合并；不直接开发 |
| `release/community-v1.2` | 社区版发布维护线 | 只接受修复和发布准备；每次发布打不可变 tag |
| `feature/encore-*` | Encore 元数据功能 | 从 Encore `main` 创建；完成后 PR 回 Encore `main` |
| `feature/community-*` | 社区版兼容、修复或数据面能力 | 从社区后端 `main` 创建；不得混入 Encore 领域实现 |
| `feature/frontend-*` | 前端页面和契约消费 | 从前端 `master` 创建；不得把开发机地址提交为发布默认值 |
| `archive/thingmodel-poc-*` | 旧 POC 保护分支 | 只读；保留历史，不再作为新功能基线 |

每个 PR 必须：

1. 只解决一个可说明的目标；跨三个仓库的改动拆成三个 PR，但共享同一任务编号和契约版本。
2. 至少一名非作者 review；改动元数据 API 时，前端/社区 adapter 的负责人必须确认兼容性。
3. 通过本仓库的 lint、单测、类型检查；跨仓变更再通过契约测试和试点租户 smoke test。
4. 不允许直接向受保护的 `main`、`master`、`release/*` push，也不允许 force push 共享分支。

### 3.3 责任边界

| 角色 | 主要负责 | 不负责 |
|---|---|---|
| Encore owner | 元数据模型、迁移、版本快照、权限、能力/命令契约、元数据 CI | MQTT 接入、海量遥测写入、旧 UI 的全部业务 |
| Community owner | 稳定发版、接入和数据面、命令执行、兼容 adapter、回退开关 | 把新的元数据规则复制进社区版 |
| Frontend owner | 当前主线上的元数据页面、契约调用、灰度 UI、E2E | 直接访问两个数据库或把服务地址写死 |
| Release owner | tag、镜像、变更单、灰度批准、回滚演练 | 未经验收替任何团队发布 |

若团队人数少，一人可兼任多个角色，但每个 PR 仍要按“哪个仓库拥有事实源”来 review，不能因为同一个人提交而跳过边界检查。

## 4. API、数据和前端的唯一性规则

### 4.1 元数据只写 Encore

从本方案启动起，以下对象只允许 Encore 写入：

- ThingModel 草稿、发布版本与不可变 Snapshot；
- DeviceTemplate 与 ThingModel 的正式绑定；
- Device 的元数据绑定、能力和命令标识符；
- 元数据迁移记录和审计记录。

社区版可以读取 Encore 的投影结果或通过 adapter 查询，但不得再维护另一套可写的物模型真相。迁移阶段保留的 `remark`、`remark1` 等旧字段仅用于导入和回退，不得成为新功能写入目标。

### 4.2 命令执行仍留在社区版

Encore 返回“可做什么、参数是否合法、谁可操作”；社区版负责“通过哪个协议下发、是否收到 ACK、遥测是否读回”。每次控制动作都带 `tenant_id`、`device_id`、`request_id`、`idempotency_key`，并保存受理、下发、ACK、读回四段结果。

### 4.3 前端只认版本化 HTTP 契约

前端调用新增路径，例如 `/api/metadata/v1/...`，由网关反向代理至 Encore；原有 `/api/v1/...` 继续到社区版。不要让同一条路径在不同环境指向不同后端，也不要提交 `127.0.0.1` 或测试站为生产默认地址。

契约变更必须先更新 OpenAPI/JSON Schema、生成或更新 mock/contract test，再改服务端和前端。字段只能新增、弃用，不能在同一主版本中改语义或复用字段名。

## 5. 从现在到“旧元数据下线”的执行顺序

### 阶段 A：收工和保护现有成果

- 为当前 Encore、前端本地提交创建远端备份分支并开 PR；不要长期让未推送提交留在 `main`/`master`。
- 将社区后端当前未提交的 SSE、WebSocket、API Key 修复单独建 hotfix PR；不要与元数据迁移混在一起。
- 给旧 `thingmodel` 分支打 `archive/thingmodel-poc-202606` tag，补一份“可复用资产清单”。
- 修复 Encore CI 验证：connector deploy command 的 `json.RawMessage` 编译问题、legacy command fallback 的 404 测试，并在可写 Go 模块缓存的环境执行 `encore check` 与 `encore test`。

**完成标准：** 所有已有代码均在远端可恢复；每条主线无未提交改动；Encore 和前端有可重复的绿灯验证。

### 阶段 B：新旧兼容，但新服务已是事实源

- 在 Encore 中导入现有模板/设备绑定，记录源 ID、目标 ID、哈希、操作者和可逆迁移记录。
- 对一个试点租户启用“Encore 写、Encore 读；社区版只执行”的路径。
- 做双读比对：同一设备的模型标识、字段、单位、访问权限、命令参数和版本必须一致；差异必须可见、可定位。
- 统计 fallback 次数、失败原因、迁移成功率、命令回执率和跨租户拒绝率。

**完成标准：** 连续两个发布周期内，试点租户无未解释的模型/权限/命令差异；所有写入都可从 Encore 审计追溯。

### 阶段 C：逐租户扩大并停写旧元数据

- 按“内部租户 → 低风险客户 → 普通客户 → 高风险客户”扩大。
- 禁止新建或编辑旧物模型；旧页面改为只读提示和迁移入口。
- 旧 adapter 仅在 Encore 不可用时提供有指标的短期 fallback，不能静默吞错或返回空数据。

**完成标准：** 新建/修改元数据 100% 走 Encore，旧写入接口 30 天无成功写请求，且灰度开关的回退演练成功。

### 阶段 D：正式退役旧物模型

仅在下列条件全部满足后执行：

1. Encore 生产环境完成备份恢复演练、迁移回滚演练和权限隔离测试。
2. 所有活跃租户的元数据已导入，且迁移校验哈希、数量、版本和抽样业务结果一致。
3. 旧元数据 API 已连续 30 天零业务流量；没有依赖它的外部集成或市场包。
4. 旧兼容读取、旧页面和 feature flag 已先关闭一个发布周期，并确认可回退。
5. 历史表/字段已有只读备份和明确保留期限；先删除代码路径，后删除数据，删除数据需单独变更单批准。

退役后的状态是：社区版仍发布、仍接入和执行，但它从 Encore 获取设备元数据；旧物模型代码不再维护。

## 6. 发布与回滚

社区版和 Encore 独立发版，互不阻塞：

| 项目 | 版本示例 | 发布条件 | 回滚方式 |
|---|---|---|---|
| 社区版 | `community-v1.2.x` | 社区后端/前端测试和升级验证通过 | 回滚镜像或 release tag；数据库迁移必须可兼容 |
| Encore 元数据 | `metadata-v0.x`，稳定后 `v1.x` | `encore check`、`encore test`、迁移 smoke、契约测试通过 | 回滚服务版本；迁移记录支持逐项回滚 |
| 跨仓契约 | `metadata-api-v1` | Consumer contract test 全绿 | 保持旧 API 版本直到所有消费者迁完 |

出现问题时的优先级：先关闭试点租户开关或网关路由，再回滚 Encore 服务；不要先修改社区版数据库或删除旧数据。这样老客户的稳定发布不被新元数据试验牵连。

## 7. 每周协作节奏

- **周一：** 确认本周的契约、负责人、试点租户和验收样本。
- **每天：** PR 只合入通过本仓库验证的改动；阻塞问题写入 issue，不在聊天里临时改协议。
- **周三：** 运行跨仓契约测试和试点 smoke；查看 fallback/错误指标。
- **周五：** 发布候选、回滚演练或明确宣布本周不发；更新迁移进度表。

一个任务的最小协作卡片应包含：目标、影响仓库、API 版本、数据迁移、验证命令、试点范围、回滚开关和负责人。没有这些字段的任务不得直接进入发布。

## 9. 验收场景

**之前：** 新建模板可能写在旧社区版路径，也可能由 Encore 读取；前端、adapter 和数据库的“谁说了算”不稳定，开关默认关闭。

**之后：** 在试点租户创建温湿度设备时，Encore 创建并发布 ThingModel Snapshot，绑定设备并返回版本化能力；前端读取 `/api/metadata/v1` 显示字段和命令；社区版仍负责向实际协议下发控制。关闭该租户路由即可回到既有发布系统，设备接入和遥测不中断。

手工验收应覆盖：创建模型、发布快照、绑定设备、读取能力、参数校验、命令审批/下发/读回、跨租户拒绝、关闭开关回退、迁移回滚。每一项必须同时留下 HTTP 结果、审计记录和监控指标。

## 10. 取舍

这个方案的优势是稳定发布和新能力可并行，职责清晰，故障能按租户回退，且最终能真正清理旧元数据代码。代价是迁移期间多一套服务、契约和测试，需要团队遵守边界。

与“直接合并旧 `thingmodel` 分支”相比，它短期多做了契约和验证，却避免把落后主线的大量代码冲突带到发布系统；与“全量用 Encore 重写社区版”相比，它更快让客户获得版本化物模型和安全控制能力，同时保留已验证的设备接入和遥测能力。

## 11. 本机运行时收工方式（已落地）

本机采用“一套平台基础设施 + 一套 Encore 开发实例”的方式，不启动两个 4000：

| 组件 | 端口 | 处理方式 |
|---|---:|---|
| Encore `devicemetadata` | 4000 | 仅运行 `iot-api-encore-kernel.worktrees/encore-thingsmodel`；ChatBridge 和能力适配器共同调用 |
| 社区版后端 | 9999 | 继续作为稳定数据面、设备接入、遥测与协议执行入口 |
| GMQTT | 1883 | 复用 ThingsPanel 平台唯一 broker；不为 Encore 再开 broker |
| ThingsPanel PostgreSQL / Redis | 5555 / 6379 | 复用平台数据层 |
| ChatBridge Redis | 6380 | 保持独立，承载 ChatBridge 状态和消费组 |
| ThingsVis Studio / Server | 3000 / 8000 | 复用现有 ThingsVis；不重复启动第二套 |
| ChatBridge / adapter / event-ingress | 8001 / 3010 / 8787 | 复用现有链路，adapter 优先访问 Encore，旧接口仅作兼容回退 |
| 执行反馈线 / 运维界面 | 19092 / 8790 | 复用现有 TPEA、Temporal、worker 和 operations UI |

对应源码和运行目录：

```bash
git -C /Users/junhong/Downloads/code/iot-api-encore-kernel worktree list
# main：官方基线
```

只有在需要第二套完全隔离的验收环境时，才再启动第二个 Encore，并为它另分端口、Encore 本地数据库/状态、Redis 命名空间和设备模拟器；不能让两个实例同时控制同一批真实设备。

## 12. 独立 ThingsModel 前端入口（已落地）

当前前端仓库的 `thingmodel` 分支包含独立的 `/thing-model`、`/device-template` 页面和 Encore API client；官方 `master` 仍是 5002 稳定页面。为了并行运行，两条前端线分开：

```text
官方社区前端 master       http://127.0.0.1:5002
ThingsModel 开发前端       http://127.0.0.1:5003
                            └─ /proxy-thingmodel/* → http://127.0.0.1:4000/*
```

本机 worktree：

```text
/Users/junhong/Downloads/code/thingspanel-frontend-community.worktrees/thingmodel
分支：feature/thingmodel-dev-20260917
```

5003 前端仍调用社区后端的 `/api/v1/login` 获取 ThingsPanel JWT；登录后把同一 JWT 以 `Authorization: Bearer` 传给 Encore。因此账号体系相同，但 5002 与 5003 属于不同浏览器 origin，需要各自登录一次，不存在独立的 Encore 用户表。
