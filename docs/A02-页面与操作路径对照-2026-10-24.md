### 2.1 当前实际操作步骤

**#1 全局场景联动（有启用开关、无草稿/发布）**
1. 列表页"新建场景联动"→ `automation_linkage-edit`（`dataList.vue:45-49`）。
2. 填名称/描述（`linkage-edit/index.vue:418-429`）。
3. IF：选"设备条件"（单设备 `10`/单类设备 `11`）或"时间条件"（单次 `20`/重复 `21`/时间段 `22`），组内 AND、组间 OR（`edit-premise.vue:144-172`、`456-472`）。
4. THEN：操作设备 / 激活场景 / 触发告警（`edit-action.vue:122-135`）。
5. 保存 → **二次确认弹窗** → `POST` 或 `PUT` → 回列表（`linkage-edit/index.vue:94-126`）。
6. 启停：卡片右上角 `n-switch`，即时 `POST /scene_automations/switch/{id}`（`dataList.vue:237-243`、`66-71`）。
7. 执行记录：卡片底部文档图标 → 弹窗，按时间范围 + 成功/失败筛选（`dataList.vue:261-272`、`139-148`）。

**#2 场景管理（无启用开关、有"激活"= 立即执行）**
1. "新建场景"→ `automation_scene-edit`（`scene-manage/index.vue:21-23`）。
2. 填名称/描述，加"执行动作"（仅"操作设备"可用，激活场景/触发告警选项被注释，`scene-edit/index.vue:93-111`）。
3. 保存 → 二次确认 → `POST/PUT /scene` → 回列表（`scene-edit/index.vue:475-498`）。
4. 列表行"激活"→ **无确认弹窗**（确认逻辑被注释，`scene-manage/index.vue:31-47`）→ `POST /scene/active/{id}`，后端立即执行动作（`BE/internal/service/scene.go:77-78`、`BE/internal/service/automate_telemetry.go:289-293`）。
5. 执行记录：行内"日志"按钮 → `GET /scene/log`（`scene-manage/index.vue:96-100`、`86-94`）。

**#3/#5 设备/模板自动化**：与 #1 完全相同的列表与表单，只是查询参数带 `device_id` 或 `device_config_id`，保存后 `router.replace` 回设备详情/模板详情（`linkage-edit/index.vue:100-124`）。

**#4/#6 设备/模板告警**
1. 告警 tab 默认显示"告警历史"（`give-an-alarm.vue:184-191`），切到"告警规则"后列表 = 含告警动作的联动规则。
2. "新增告警规则"→ `linkage-edit`（带 `device_id`/`device_config_id`、`backType`）。
3. 在 THEN 里选"触发告警"并选一条**告警配置**（`alarm_config`，来自 `GET /alarm/config`，`scene-edit/index.vue:364-370`、`867-878`）——即"告警规则"= 联动 + 告警动作，不是独立的告警对象。
4. 启停/日志/删除复用 `dataList`。

**告警配置（`/alarm/warning-message` 的第二个 tab）**：名称/级别/通知策略，`POST /alarm/config`；启停走 `PUT /alarm/config {ID, enabled}`（`new-information.vue:48-60`、`232-241`）。表单中"触发重复次数/持续时间"两项**模板已注释**（`pop-up.vue:405-421`），且旧表**无这两列**（`BE/internal/model/alarm_config.gen.go:14-26`），提交值被后端丢弃。

## 7. 待确认项

1. **自动化父菜单与两个子菜单的来源**：代码与 `BE/sql/*.sql` 均无种子（检索 `scene-linkage|scene-manage` 无命中），实际记录在目标环境 `sys_ui_elements` 表中。冻结菜单前需导出该表核对 `route_path`/`authority`。
2. **生产环境如何路由到 Encore**：目前只有开发态代理先例 `/notification-core`（`FE/build/config/proxy.ts:27-48`），生产反代规则未见。`/v1/*` 的对外前缀需与部署确认，否则前端要改 baseURL 才算"少改"。
3. **"场景"在新模型中的表示**：`Validate` 对所有 kind 都强制"至少一组触发条件"（`EN/automation/domain/validate.go:58-60`），而旧场景无触发、只手动执行（`BE/internal/model/scene_info.gen.go:14-23`）。要么允许 `kind=scene` 空触发，要么补"手动场景"语义；否则用户被迫编一个触发条件——直接违反"不多一步"。
4. **告警规则的归属**：`kind=alarm_policy` 与"含告警动作的 automation"如何二选一，需产品确认；影响 R4 的迁移数量。
5. **执行记录的结果枚举映射**：旧 `S/F`（`dataList.vue:109-122`）→ 新 `RunResponse.status/reason_code`（`EN/automation/api_types.go:194-196`）的对应表未定义。
6. **`alarm_config` 的 `alarm_repeat_time/alarm_keep_time`**：前端仍提交（`pop-up.vue:307-308`）但表无此列（`BE/internal/model/alarm_config.gen.go:14-26`），现网等价于"从未生效"。切新接口时不要把这两个字段当成"已有功能"平移。
7. **场景"激活"无二次确认**（`scene-manage/index.vue:31-47` 确认逻辑被注释）：是否保留现状需产品确认；若保留，误点即真实下发设备指令。
