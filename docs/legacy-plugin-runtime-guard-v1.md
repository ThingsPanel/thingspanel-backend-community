# Legacy plugin runtime guard — unfinished J1/J6 capability

The original Gin routing group exposed five plugin runtime POST routes before user authentication: heartbeat, device/config, devices, service/access/list, and service/access. Their owner functions use legacy service/access identifiers, without a verified current managed instance and durable binding. The resource-read paths can return device configuration or credentials; heartbeat is a write.

The integration branch now attaches `middleware.RejectUnboundPluginRuntime()` before all five original handlers. It returns HTTP 503 with `PLUGIN_RUNTIME_IDENTITY_REQUIRED`, `state=blocked`, `automatic_retry=false`, and `Cache-Control: no-store`, before binding/parsing or owner execution. It does not echo submitted identities or credentials. User tokens and caller-supplied active/instance/tenant headers cannot bypass it. There is no enable flag for the anonymous behavior.

This deliberately leaves a capability unavailable. It does not implement plugin identity, durable generations, activation, SDK execution fences, or final approved route retirement. Existing business owner functions and routes are retained for the controlled transition. No production deployment or actual plugin stop was performed by adding this branch change.

Owner: team A for current business authorization, binding and receive-side fences; team B for Agent process/container execution and recovery. The total lead owns this shared router edit. Restore supported operations only through the existing owner with trusted service/Agent/plugin identities, exact tenant/instance/purpose, current binding and independent generations, revocation and expiry. Provider/consumer tests must prove that inactive, paused, superseded, disconnected and restarted old instances cannot produce side effects. Validate the real SDK/Broker paths, not only this HTTP rejection.

`go test -count=1 -v ./internal/middleware -run '^TestLegacyPluginRuntimeGuard'` verifies actual Gin middleware behavior with explicit untrusted headers and an owner side-effect sentinel. It is a narrow HTTP test, not a real database, deployed router, or whole SDK execution test. The root router package also needs compilation after integration.
