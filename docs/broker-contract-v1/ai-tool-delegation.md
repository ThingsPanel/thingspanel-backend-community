# Community AI tool delegation v1 — implementation decision

Status: opt-in implementation with isolated PG/Redis/HTTP and runtime-RPC integration evidence after engineering checkpoint ba4ccecd; no deployed tool or credential issuer is claimed. This adds an opt-in API contract and an ephemeral authorization record, not an AI runtime or device/model master.

## Trust boundary

A human holding an existing valid ThingsPanel session may issue a 120-second opaque, random 256-bit tool token for at most 16 explicit same-tenant active/enabled devices and selected fixed operations: devices.describe, telemetry.query, commands.preview, commands.getResult. Each token allows at most 20 attempted authorized-scope calls. No authorize, submit, arbitrary URL, HTTP header, SQL, MQTT publish, or tenant/user override exists on the delegated surface. Replay tokens use only read operations.

The tool token is distinct from a user JWT and is not stored as a valid JWT session key, so it cannot authenticate the existing human command authorization/submission endpoints. The server retains the parent session privately for forwarding to the existing semantic owner; only the trusted server-side tool adapter receives the scoped opaque token. The model receives no credential: neither parent JWT nor opaque bearer may enter tool arguments, prompts, tool outputs, traces or logs. Every call revalidates the original JWT, Redis session, current user/tenant/authority, device scope, and explicit operation capability in the existing Casbin owner. Each fixed api/v1/broker-ai/tools/{operation} route must have an installed g2 mapping and an effective allow policy; a missing policy fails closed even though legacy human routes may allow unconfigured paths. Parent logout/revocation or grant revocation fails closed. A command preview remains only a proposal; a human uses the existing authenticated plan flow to approve/submit separately.

Redis holds a SHA-256-derived token key, a private immutable body and an atomic remaining-call counter with TTL. Atomic Lua issuance/call accounting and expiring per-user/per-tenant indices bound active grants (8 per user, 1,000 per tenant). Redis time/TTL determines expiry; host clocks are not used to prove grant lifetime. Scope is checked against the private immutable body, then a Lua compare of those exact bytes, positive TTL and remaining counter atomically consumes the call. Revocation removes the body and makes a stale pre-read fail at this linearization point. A call consumed before revocation is an already-authorized in-flight read/proposal and may finish; revocation prevents subsequent consumes. Invalid scope/device is rejected before database/semantic access; authorized-scope attempts consume quota before the parent-session check to bound revoked-session attempts too. The original token and private grant body must never enter model-visible data, errors, operation logs, or audit receipts.

## API layout and logging

The issuer, revoke and delegated-tool routes must mount before both the global OperationLogs middleware and the ordinary v1 JWTAuth/Casbin route group. The legacy OperationLogs middleware captures full POST response bodies. Issuance uses an existing human x-token and server-parsed claims, then ValidateBrokerSubject; it does not accept actor or tenant fields. Revocation uses a public delegation ID, not a bearer in a URL. Delegated routes accept Authorization: Bearer only and reject conflicting x-token credentials. All routes return Cache-Control: no-store and bounded JSON bodies before parsing. Model-visible results are capped at 64 KiB; overflow fails with budget_exceeded, and an exact credential echo from an upstream fails closed rather than being logged or returned. Feature mqtt.ai_tools_enabled defaults false and requires ingress_v1 with route fencing; command preview additionally requires the existing command-plan flag.

Issuer replies and every successful tool response carry server-derived tenant_id and subject_id. A runtime adapter must compare the response identity, operation and device with its trusted actor/thread binding before exposing data; caller-supplied issuance metadata alone is not identity proof. Operations call existing Device/CommandData owners. telemetry.query uses the already bounded trusted receipt query. getResult requires an explicit granted device and a same-user command in the existing command store; it does not fall back to globally scoped legacy lookups. API errors use fixed categories and never include database, Redis or upstream raw errors.

## Runtime integration and release limits

Reuse ChatBridge AgentRuntimeKernel/RuntimeDispatcher via a fixed-origin adapter and a trusted session binding. The model cannot supply credentials, URLs, actor context or installation metadata. No ChatBridge or Encore source is copied into this Apache community repository. A live installation/delegation handoff, revoked-session checks, tool budgets, replay isolation and adversarial trials remain necessary before enabling it. This design does not assert per-tenant model-token budgets or completion of AI blind/operator studies.

## Bounded runtime transport

The optional existing-runtime adapter uses a fixed Go transport executable with JSON over stdin/stdout, never a shell or credentials in argv/env. The Go client has a total five-second HTTP deadline and a 64 KiB response cap; the Python adapter additionally kills a transport subprocess at six seconds. Fixed operations and origin are configured by the trusted server. It is a small transport shim, not a second agent framework. Live runtime registration, human-session-to-thread exchange and deployment remain unverified.
