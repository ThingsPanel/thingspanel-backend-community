# Broker owner service grants

Service credentials are explicit broker-cell and broker-instance allowlist entries. A service grant may subscribe to authenticated ingress or state streams without device targets when it has no publish permissions.

Ordinary service `Policy.Publish` entries require `AllowedDeviceIDs`. The owner resolves every ID and grants only active, enabled devices whose tenant is either listed in `AllowedTenantIDs` or, when that list is empty, equals the service principal's `TenantID`. Device IDs and tenant IDs are literal values; wildcards are rejected. A service grant is limited to 256 targets, duplicate device numbers are rejected, and a grant larger than 1 MiB is denied with `grant_too_large`.

Publish filters must use a finite canonical reply or control family. The owner replaces the device-number level with the resolved target numbers and retains `+` only for message IDs. Custom mappings and plugin aliases require the existing owner-resolved mapping/transport proof; they cannot be supplied as arbitrary service publish filters. These checks scope each grant to its selected device IDs; application entrypoints must independently enforce caller authorization.

## First-party target publisher

`target_scoped_publisher: true` permits a service to open a separate connection for one current target. The client ID is generated by `brokercontract.TargetPublisherClientID` from an explicitly allowed base client ID and the target ID. This selector is not a credential: username, password, broker cell/instance and base client allowlist remain mandatory. Target connections have no subscriptions. Without a static target list the base connection retains only its declared subscriptions.

`target_tenant_scope` has two modes:

- Omitted or `tenant`: an explicit `allowed_tenant_ids` list is required. Fresh device resolution must belong to that list. Existing ordinary service behavior is unchanged.
- `platform`: reserved for the first-party application publisher. Both static device and tenant lists must be empty. The owner derives the tenant from the one current active/enabled target record, so newly created tenants and devices require no manual list maintenance. This mode is forbidden for `plugin_socket`, `allow_any_client_id`, and services that have not opted in to target publishing. It gives the service a platform responsibility, but each MQTT grant still contains only one target's exact finite topics.

Enable `mqtt.target_scoped_publisher` in the application only after deploying an owner that supports this contract and configuring its dedicated first-party service identity. Do not share that identity with tenant callers or protocol plugins. Commands continue to use business-layer tenant validation, durable caller validation and delivery-time route/mapping fences; attribute/event ACKs use the authenticated ingress device identity.

The application pool has at most 32 target connections, serializes each target's sends, reconnects before a send after 45 seconds, and releases 30-second-idle connections on its 5-second sweep. Sessions are clean and automatic reconnect is disabled. A failed or ambiguous publish is not retried by the pool. Owner grants expire within 60 seconds; an already issued ACK grant can remain valid until that deadline. Reconnecting always resolves current device state again. Runtime fencing and command frame tenant/target/epoch/mapping/expiry checks remain in force; the 45-second refresh is not a claim of instantaneous revocation.
