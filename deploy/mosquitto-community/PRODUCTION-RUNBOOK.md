# Community broker production image

This profile builds Mosquitto 2.1.2 and `libtp-mosquitto-plugin.so` from the same source headers, then packages only the broker executable, plugin, fixed broker configuration, owner executable, readiness tooling, and the `tp-broker-audit` operator utility. The image also contains the broker-owner executable; Compose runs it as a separate process using the same image. Both processes run as UID/GID 1883. The final container root filesystem can be read-only; only `/mosquitto/data` needs persistent write access.

The source commit is `99fa50f30e325609394c324c8ff71cfbbe95d8ab`. The Debian and Go OCI index digests, with their platform manifests, are recorded in `base-images.manifest`. The build pins the index digests. Debian apt packages are still fetched from the live Debian repositories during a build, so preserve the resulting image digest and build SBOM as release evidence.

## Build and inspect

Run these commands from the repository root after reviewing the source commit and base image manifest:

```sh
docker buildx build --platform linux/arm64 --load \
  -f deploy/mosquitto-community/Dockerfile.production \
  -t thingspanel-community-broker:reviewed .
docker image inspect thingspanel-community-broker:reviewed \
  --format '{{.Id}} {{json .RepoDigests}}'
docker save thingspanel-community-broker:reviewed | shasum -a 256
syft thingspanel-community-broker:reviewed -o spdx-json=community-broker.spdx.json
```

Record the image ID, archive checksum, SBOM, source commit, build platform, and builder version with the release. Inspect the final filesystem and confirm that it contains no repository checkout, source tree, token, service policy, DSN, or TLS key. The plugin `.so` is compiled with CGO against `/opt/mosquitto/include`, copied from the Mosquitto source build in the same Docker build.

## Stage runtime secrets

Provide three files through the deployment secret manager:

* Owner token JSON: `[]brokercontrol.TokenBinding`, binding the secret token to the chosen logical broker cell and broker instance.
* Service policy JSON: `[]brokercontrol.ServiceCredential`, with finite `AllowedClientIDs`, tenant/device scope for every service that can publish, and explicit subscriptions for `tp-internal/ingress/v1/#` and `tp-internal/state/v1/#` as needed.
* The raw plugin token corresponding to the owner token JSON entry.

The Compose example uses file-backed secrets for demonstration. Set their host ownership to numeric `1883:1883` and permissions to `0440`; verify readability as UID 1883 before launch. File-backed Compose secrets can retain host ownership and mode, so do not assume Compose rewrites them. Never put secret contents in the repository, image, or shell history. Supply `TP_BROKER_OWNER_DATABASE_DSN` through the deployment secret/environment mechanism supported by the target runtime.

The owner and broker share a network namespace. The plugin calls the owner at `http://127.0.0.1:9801`, which satisfies the driver's loopback-only cleartext HTTP rule. No owner port is published on the host. The broker's example listener is plaintext MQTT on 1883; place it on a private network or behind an MQTT-aware TLS termination layer before accepting remote device traffic. TLS passthrough requires a separately reviewed Mosquitto TLS listener and certificate configuration, which this example does not provide. The example deliberately leaves port publishing and the external TLS boundary to the operator.

The broker configuration has `allow_anonymous false` and an explicit mandatory plugin path. Do not override the config with a listener that omits either setting. Run with a read-only root filesystem, dropped capabilities, `no-new-privileges`, and a writable persistent `/mosquitto/data` volume.

## Strict route-fencing profile (explicit opt-in)

The production Compose example intentionally leaves runtime route fencing disabled. Enable it only after the dedicated strict-profile migration/barrier acceptance is complete. The broker container requires `TP_BROKER_ROUTE_FENCING=1`; the ThingsPanel backend config must set `mqtt.route_fencing: true`, `mqtt.input_profile: ingress_v1`, a stable per-replica `mqtt.runtime_instance`, and the matching `mqtt.broker_cell`. The stable instance identifies membership; each backend process start creates a fresh boot generation. Migration 012 must be installed before starting a fenced backend. Missing schema, an unavailable Owner, malformed/overflow response, or expired 10-second control lease fails closed. Do not enable this flag on the default legacy profile or treat the runtime sync endpoint as a route-admin API. Route prepare/freeze/activate operations still require an authorized control-plane workflow and their own evidence.

## Readiness and authentication check

The owner healthcheck verifies only that its local TCP listener accepts connections; that is liveness and does not establish schema readiness. The broker healthcheck uses Paho with the explicitly allowlisted readiness client identity, authenticates against the running broker, and waits for a SUBACK on `tp-internal/state/v1/#`. Add `tp-community-readiness` (or the configured readiness client ID) to one service's `AllowedClientIDs`, and grant that service the state filter. This proves the owner grant path and an authorized subscription are working. It does not prove that a device can authenticate or publish.

Before production exposure, run a separate device-level acceptance using a dedicated test voucher and verify both the expected authorized topic and a denied topic. Avoid testing on shared production listeners. Capture the broker/plugin version, image digest, connection result, SUBACK, and the application receipt separately; a device PUBACK is protocol acknowledgement and does not prove application processing or physical effect.

## QA migration and rollback drill

Run `deploy/mosquitto-community/drill-migration-rollback-qa.sh` with `TP_BROKER_MIGRATION_DSN` pointing only at the dedicated database named `brokerqa`. The script creates a random `mqtt_qa_drill_*` schema, applies and reapplies all numbered migrations, checks the required columns and `broker_safe_voucher_v1(text)`, starts a temporary anonymous MQTT listener bound only to `127.0.0.1` on an OS-assigned port, performs a local subscribe/publish smoke test, then drops only its generated schema and stops only its child broker. `MOSQUITTO_BIN`, `MOSQUITTO_PUB`, and `MOSQUITTO_SUB` may select local test binaries. It never selects a device, changes a transport binding, accesses production ports 1883/9999, or exercises the production owner/auth path.

This drill validates schema repeatability and cleanup, not application deployment or route rollback. SQL migration 012 provides a route-change state machine, runtime participants register and acknowledge through the Owner, and `tp-broker-route` inspects route state. `tp-broker-cutover` applies reviewed, byte-hash-bound plans for freeze/prepare/activate/rebase; it cannot create runtime acknowledgements or skip a barrier. There is no operator workflow for membership retirement, and the isolated native single-binding A/1→B/2→A/3 test does not cover complete profile/command/legacy gray rollout or operational rollback, so these components do not yet establish operational cutover readiness. See `CUTOVER-CLI.md`; do not use ad hoc SQL updates as an operational substitute.

## Database and release evidence

Install and review the broker schema migrations `sql/broker/001_broker_owner_tables.sql` through the latest numbered file (currently `014_telemetry_evidence_index.sql`) using the normal database migration process before enabling ingress. The owner and application must use the intended tenant schema/search path. The binary does not auto-migrate production databases. Validate required columns, `broker_safe_voucher_v1(text)`, and indexes before enabling the `ingress_v1` input profile. Migration 011 creates the voucher expression index with ordinary `CREATE INDEX` when `devices` exists; schedule it in a maintenance window because index creation takes a write lock. If the broker schema is installed before the core `devices` table, rerun migration 011 after core bootstrap to create that index. Migration 014 adds the partial expression index used by the telemetry evidence API. That API queries processed `trusted_telemetry_batch` receipts only. The current writer stamps its timestamp from broker observation time and does not preserve an independent device-reported time, so API `reported_at` is null and `reported_time_available` is false; `observed_at` is receipt `created_at`, and `processed_at` is when the trusted batch committed. It does not report a backend arrival time because the schema does not store one.

`check-broker-schema.sh --schema public` is read-only by default and returns nonzero when required columns, the voucher function, or required named indexes are missing. Its apply mode is test-only: numbered migrations run in order only with `--apply --target qa --confirm-qa-apply`, a schema named `mqtt_qa_*`, and a connected database named exactly `brokerqa`. Production migration remains an explicit operator-controlled step through the normal migration process; this checker refuses apply for `public` and any other database. Reapplying the current `IF NOT EXISTS` DDL migrations to the same isolated schema is supported. The checker has no migration ledger or checksums and does not verify index definitions or production data; keep reviewing migration SQL and index state through the normal deployment process.

For each release retain the migration revision, image digest, checksum, SPDX SBOM, resolved base image manifest, secret file ownership/readability check, authenticated readiness result, device authorization test, and first application-level receipt. Keep receipt processing, broker acknowledgement, device acknowledgement, and physical command completion as separate evidence states. An `expired` or `broker_acknowledged` command state alone does not establish a physical outcome.

The runtime image preserves the pinned Mosquitto source license files at `/usr/share/licenses/mosquitto/LICENSE.txt`, `/usr/share/licenses/mosquitto/epl-v20`, and `/usr/share/licenses/mosquitto/edl-v10`; the repository `LICENSE` text is included as `/usr/share/licenses/mosquitto/thingspanel-community-LICENSE`. These are the original texts copied into the image.

## Experimental semantic evidence and planned commands

The additive read-only endpoints are `GET /api/v1/device/status/evidence/:id` and `GET /api/v1/device/semantic/evidence/:id`. Status returns `online`, `offline`, or `unknown` with freshness and an as-of time, never rewriting legacy `is_online` during a read. Semantic evidence requires `mqtt.input_profile=ingress_v1`, a fixed `mqtt.semantic_base_url` HTTPS origin, and the original authenticated user `x-token`; API keys cannot masquerade as delegated user sessions. Loopback HTTP requires the explicit development flag `mqtt.semantic_development_http=true`. Reads use the existing Encore device/template binding and its exact canonical published snapshot; missing/unconverted bindings are unsupported, never silently replaced with latest. The live authenticated Encore deployment is still unverified.

`mqtt.command_plans_enabled` defaults false. This experimental API additionally requires route fencing, SQL013 and a fresh positive state observation. Preview/authorize/submit live under `/api/v1/command/datas/plans`; authorization is a separate human-session operation and must never be registered as an LLM tool. One plan authorizes at most one command even with different idempotency keys; command/log/plan consumption is atomic in the existing command owner. Plan TTL is at most two minutes (default 30 seconds), with at most 256 valid unconsumed plans / 16 MiB of canonical+encoded payload per tenant. Revoked/disabled caller, changed state/configuration/route, changed published binding before submit and unsupported typed schema reject execution. Dispatcher revalidates the SQL state and command snapshot under the transport binding lock. An immutable semantic snapshot is pinned, but the remote Encore binding read is not a distributed transaction with community SQL; this limitation must be addressed or explicitly accepted in a certified profile before claiming atomic cross-service model changes. No AI provider/orchestrator, blind benchmark, physical-action result or G5 approval is implied by these primitives.

In the current `ingress_v1` candidate, raw legacy telemetry/attribute control, attribute query downlinks, OTA and expected-data dispatch are explicitly rejected before enqueue. Durable canonical CMD and application report responses have their separate supported paths. Legacy profile behavior remains available. These are real compatibility gaps pending a durable-owner integration, not N/A assertions or proof that no customer uses them. Do not migrate a binding that requires an unsupported family.

## Experimental delegated AI tools

`mqtt.ai_tools_enabled` defaults false and additionally requires `ingress_v1` and route fencing. Enable it only on an isolated reviewed candidate. Human session holders can issue/revoke short-lived delegations at `POST /api/v1/broker-ai/delegations` and `POST /api/v1/broker-ai/delegations/:id/revoke`. Issuance takes `device_ids`, `scopes`, and optional `replay`; it never accepts tenant/user identity. Four delegated POST routes under `/api/v1/broker-ai/tools/` support only `devices.describe`, `telemetry.query`, `commands.preview`, and `commands.getResult`. Preview additionally requires `mqtt.command_plans_enabled` and cannot authorize or submit a command.

Install each selected `api/v1/broker-ai/tools/{operation}` capability through the existing Casbin owner: the exact route requires a `g2` mapping and an effective current user/role allow policy. Missing mappings fail closed; enabling the feature alone grants no capability. Keep normal human authorization separate. Each grant is limited to 120 seconds, 20 authorized-scope attempts, 16 devices, and explicit operations; issuance is capped at 8 active grants per user and 1,000 per tenant. Parent-session logout, disabled users/devices, changed authority, current policy denial, expiry and revocation reject subsequent calls. This implementation uses the existing standalone Redis owner; cluster/failover quota semantics have not been certified.

Credential routes register before full-body operation logging. The parent JWT and opaque token must remain in the trusted server adapter; do not place them in model arguments, prompts, command lines, URLs, environment variables, response traces or application logs. A successful tool response contains server-derived tenant/user/operation/device bindings that the adapter checks before exposing inner data. The complete JSON response is bounded to 64 KiB. The optional fixed-origin transport and runtime adapter require explicit installation and trusted thread binding; this repository does not enable or deploy a ChatBridge integration automatically. See the [delegation contract](../../docs/broker-contract-v1/ai-tool-delegation.md) and [executed integration evidence](../../docs/gmqtt-evidence-2026-10-20/ai-delegation-test-plan.md). Live Encore, real model evaluation, tenant model-spend budgets, operator studies and physical outcomes remain separate gates.
