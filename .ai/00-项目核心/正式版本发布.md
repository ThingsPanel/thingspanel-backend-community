# 正式版本发布

## 职责与边界

已完成发布配置，实际镜像发布待执行：前端 master、后端 main 各发布同名版本标签；日常源码推送仍只走测试服部署。发布工作流只读取标签代码，不能把本地未提交的场景执行改动打包。用户本次不再进行业务回归，也不立即创建 Release。

后端统一 Release 入口协调二进制包、社区镜像、Encore 镜像与 Linux Compose 包。Encore 使用已验证的 1.58.6 CLI 构建同一镜像，由运行配置分别启动原生业务与通知核心，不内嵌凭据。Mosquitto 复用已有固定源码与插件生产 Dockerfile，Broker/Owner 共用独立镜像，作为新版 Linux 部署的必要组件一同发布。

## 发布顺序

1. 发布前端同版本 Release，按标签以 Node 20.19.0、pnpm 10.8.0 和锁文件构建静态包及 amd64/arm64 镜像。
2. 发布后端同版本 Release，协调后端静态包、社区/Broker 镜像及 Encore 双架构镜像推送到既有三个仓库。
3. 仅在这些任务成功，且同版本前端镜像/静态包已就绪后，生成带各组件源码提交和阿里云镜像摘要的 Linux Compose 部署包。缺少组件则明确失败，前端后补后可重跑打包任务。

Windows EXE 仍是 GMQTT 旧架构，按用户明确决定暂停自动触发；本次不修改外部 Windows 安装器，不声称其支持 Encore。

## 关键规则

- 标签必须是带 v 前缀的明确版本，禁止 latest、猜最新标签或以当前分支代码冒充标签。Release 与手工重建都固定同一标签提交。
- 镜像完成全部目标仓库推送并校验双架构后才记录可用清单；部署包按摘要引用镜像。没有发布镜像时不能把静态检查当成真实推送成功。
- 前端默认同源 /automation-core 转发到 Encore，明确拒绝其内部服务路径；原生物模型和通知路由保留正确服务边界。
- 部署包保留各服务独立运行、数据库和定时唤醒配置；运行凭据由部署者私有准备，不打包测试服数据或凭据，不自动覆盖现有环境。

入口：.github/workflows/release.yml、docker-image-build.yml、encore-image-build.yml、build-release.yml，deploy/release/；前端 .github/workflows/docker-image-build.yml、buildAndRelease.yml 和 nginx.conf。交付说明链接工作区 AGENTS.md 的版本发布入口。
